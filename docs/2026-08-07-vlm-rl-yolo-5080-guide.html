1. 대화의 출발점

목표는 주문이 들어오면 물품 입고·출고를 위해 최적 동선을 만들고, 이를 좌표 시퀀스로 관리하는 것이다. 예시 경로는 냉동 창고 → 상온 창고 → 포장대 → 대기/충전소 복귀다.

기본 운행은 Nav2가 맡고, Nav2가 자체 costmap·기본 recovery로 대응하지 못하는 위험·예외 상황에만 YOLO, VLM, RL을 개입시킨다. 이 문서에서 말하는 VLM은 Expert, RL은 Explorer이며, 둘 다 안전 승인자가 아니라 복구 제안자다.

가장 중요한 원칙: VLM/RL은 전역 교통·예약을 결정하거나 cmd_vel을 직접 발행하지 않는다. FMS는 전역 작업·예약, Nav2는 즉시 로컬 주행, Safety Supervisor는 최종 허용·정지 권한을 가진다.

IROS — VLM을 계속 부르면 느리고, 안 부르면 의미 판단이 약해지는 문제

풀려고 한 문제

실내 이동 로봇은 복도·교차로·표지판·방 번호처럼 의미 정보를 이해해야 하지만, VLM을 카메라 프레임마다 호출하면 지연이 너무 커진다. 논문은 SLAM 같은 기하 기반 방법은 위치 추정에는 강하지만 사람 대상 표지·문자 이해가 약하고, VLA의 반응형 판단은 보이지 않는 교차로·먼 거리 단서 추론에 한계가 있다고 문제를 정의한다. 특히 직선 복도에서는 reasoning 결과가 거의 같은데도 VLM을 반복 호출하는 낭비를 핵심 문제로 본다.

제안한 방법 — System One / System Two 이중 경로

  • System One: segmentation, OCR, key-frame compare(KFC), condition matching으로 빠르고 명확한 장면을 처리한다. 구조 변화가 감지될 때만 vision-condition matching을 수행한다.
  • System Two: System One이 모호하다고 넘긴 장면만 compact VLM이 숙고한다. System One이 만든 공간 단서와 문자 단서를 prompt에 넣어 VLM의 약한 공간 이해를 보완한다.
  • 실행: 두 경로 중 하나가 낸 Action을 finite-state action executor가 실행·확인한다.

논문 실험에서는 System One이 약 0.7~0.9초, System Two가 약 17~19초의 처리 시간을 보였으며, VLM-only 대비 지연을 줄이는 것이 구조의 핵심 성과다.

한계와 읽을 때의 주의점

  • 논문의 실험 대상은 표지판·방 번호가 있는 실내 건물 이동이다. 동적 작업자, 다중 로봇 예약, 냉동 환경 결로, 물류 작업 순서를 직접 검증한 연구는 아니다.
  • System Two 지연은 여전히 크다. VLM을 덜 부르는 구조이지, VLM 자체가 즉시 안전 제어를 할 수 있다는 뜻은 아니다.
  • turnover를 보수적으로 잡아 필요한 경우를 놓치지 않도록 했지만, 관리 가능한 장면도 VLM으로 넘기는 false positive가 발생한다. 즉 안전성과 효율 사이의 threshold 튜닝 문제가 남는다.
  • 조건-행동 표와 KFC threshold가 환경에 맞아야 한다. 창고 구조·조명·결로 변화에서 그대로 재사용할 수 없다.

Trihouse에 가져올 점

가장 직접적인 설계 참고 논문이다. 다만 System One을 YOLO + LiDAR/local costmap + Nav2 상태 + stream health로 재구성한다. YOLO는 상시 동작하고, 사람/통로 차단/미지 객체/결로 의심/반복 Nav2 실패처럼 의미 판단이 필요한 경우만 5080의 VLM으로 넘긴다. VLM에는 원본 프레임만 주지 말고 YOLO track, costmap 점유, 현재 stage, 후보 안전 node를 함께 제공한다.

그대로 가져오면 안 되는 점

IROS의 조건-행동 matching이나 VLM Action을 Pinky의 직접 주행 명령으로 연결하면 안 된다. Trihouse에서는 VLM 출력이 risk_label과 candidate_node_id, 제한된 recovery skill 제안에 머물고, Safety Supervisor와 FMS 예약, Nav2가 실행을 결정한다.

NaVILA — 언어 지시를 저수준 로봇 관절 행동으로 바로 번역하기 어려운 문제

풀려고 한 문제

Vision-and-Language Navigation에서 “왼쪽으로 돌아 75cm 전진” 같은 언어·시각 지시를 받아, 다족·휴머노이드의 복잡한 저수준 관절 행동으로 바로 바꾸는 것은 어렵다. VLM/VLA의 의미 일반화와 실제 보행 정책의 실시간·물리적 안정성 사이에 큰 간극이 있다는 것이 논문의 문제 설정이다.

제안한 방법 — 중간 수준 공간 지시를 매개로 한 2계층 구조

  • 상위 VLA: 시각·언어 입력을 바로 관절 torque로 내지 않고, “전진 75cm”, “오른쪽 30도 회전” 같은 언어 기반의 중간 수준 spatial action으로 낸다.
  • 하위 locomotion RL policy: 상위 지시를 받아 실시간으로 실행하고 장애물을 회피한다. 논문은 LiDAR를 사용해 직접 환경과 상호작용하며 학습한 vision-based locomotion policy를 제시한다.
  • 학습·평가: 실제 human touring video, simulation indoor navigation, QA 데이터를 활용한 VLA와 IsaacLab 기반 물리 benchmark, 실제 legged robot 실험을 결합한다.

한계와 읽을 때의 주의점

  • 핵심 대상은 사족·휴머노이드 보행이며, 바퀴형 AMR의 map-based Nav2 stack과 action space가 다르다.
  • 하위 policy는 rough terrain·투명 표면 같은 보행 특성까지 다룬다. 이는 창고 평면 주행의 핵심 난제와 다르다.
  • VLA와 별도 locomotion policy, 다양한 데이터, 물리 simulator가 필요하므로 초기 PoC의 구현 범위가 크다.
  • 전역 작업 배정, 다중 로봇 교통, 구역 예약, 작업자 비상 대응은 논문의 중심 문제가 아니다.

Trihouse에 가져올 점

가져올 것은 계층 분리 원리다. VLM은 “어떤 의미적 복구가 필요한가”와 “어느 안전 node가 적절한가”를 중간 수준으로 제안하고, Nav2가 실제 local/global path와 속도를 계산한다. 즉 NaVILA의 mid-level action을 Trihouse에서는 candidate_node_id, avoid_zone, recovery_skill로 바꿔 사용한다.

그대로 가져오면 안 되는 점

VLA가 cmd_vel 또는 wheel velocity를 직접 내고 Nav2를 대체하게 하면 안 된다. Pinky에서 RL은 보행 policy 역할이 아니라, 허용된 복구 skill 또는 검증된 안전 node 후보를 고르는 역할에 제한한다.

원문: arXiv NaVILA 논문 · 공식 프로젝트 페이지

EE-RL — 드물지만 치명적인 위험 사건을 일반 RL이 충분히 배우지 못하는 문제

풀려고 한 문제

End-to-end 자율주행 policy는 정상 운전 데이터에서는 잘 작동해도 보행자 횡단, 장애물 회피, 신호 위반처럼 빈도는 낮고 안전 영향은 큰 sparse-critical 상황에서 성능이 떨어진다. 일반 RL은 sparse reward와 탐험 효율 문제를 갖고, 단순 imitation은 보지 못한 위험 상황으로 일반화가 약할 수 있다는 배경에서 출발한다.

제안한 방법 — Explorer, VLM Experts, Dual Replay, StateHash

  • RL Explorer: 환경과 상호작용하며 행동을 선택하고 exploration experience를 만든다.
  • LoRA fine-tuned VLM Experts: regular scenario와 sparse-critical scenario의 reasoning·reward generation을 보조하는 여러 expert를 둔다. 학습이 진행되면 한 VLM expert가 sparse-critical reasoning에 집중한다.
  • Dual replay buffer: explorer와 expert가 만든 경험을 나누어 저장·샘플링해 policy 학습 효율과 안정성을 높인다.
  • StateHash: RGB 이미지 유사도와 차량 kinematic 유사도를 따로 비교해 이미 본 유사 상태에서는 불필요한 VLM reasoning을 건너뛴다.

한계와 읽을 때의 주의점

  • 실험은 CARLA Leaderboard의 end-to-end 자동차 주행이다. 조향·throttle을 내는 자동차 controller와 Nav2 기반 AMR은 안전 경계와 실행 단위가 다르다.
  • VLM expert·reward의 품질, StateHash 유사도 기준, dual buffer의 sampling 비율이 성능을 크게 좌우한다. 오류 난 VLM 판단이 replay에 누적될 위험도 관리해야 한다.
  • 논문이 제시하는 사고·신호 위반 수치는 CARLA 환경의 결과다. 작업자·냉동 결로·실제 Wi-Fi 지연이 있는 창고 현장 성능을 의미하지 않는다.
  • 저자도 large-model-guided RL에서 inference latency와 hallucination을 과제로 언급한다. 따라서 VLM을 실시간 safety layer로 쓰는 해석은 부정확하다.

Trihouse에 가져올 점

이 논문에서 가장 가치 있는 부분은 rare-critical experience를 일반 경험과 분리하는 관점이다. Trihouse의 critical buffer에는 person_on_path, blocked_aisle, low_visibility_condensation, localization_suspect, 반복 Nav2 failure를 저장한다. StateHash도 가능하지만 사람 검출, 급격한 LiDAR 변화, safety event가 있으면 무조건 cache를 무효화해야 한다.

그대로 가져오면 안 되는 점

EE-RL처럼 raw sensor에서 직접 자동차 control을 내도록 만들지 않는다. VLM은 구조화된 위험 의미를 내고, RL은 WAIT/BACKOUT/REOBSERVE/REQUEST_REPLAN 같은 allowlist skill만 고른다. FMS는 예약·전역 재계획을, Nav2는 실제 회피를, Safety Supervisor는 최종 거부·정지를 담당한다.

TGRPO — 성공 시연만 모은 VLA를 낯선 환경에 적응시키기 어려운 문제

풀려고 한 문제

VLA는 대규모 사전학습 뒤에도 새로운 작업·환경·실행 편향에 적응하려면 fine-tuning이 필요하다. 기존 SFT는 사람이 수집한 성공 trajectory에 크게 의존하므로 실패로부터 배우기 어렵고, 실제 환경 feedback을 충분히 활용하지 못한다. 반대로 긴 로봇 작업에 RL을 적용하면 sparse reward, 높은 variance, credit assignment 문제가 커진다.

제안한 방법 — LLM 보상 구성 + trajectory-wise group relative optimization

  • dense reward 구성: LLM의 task analysis를 이용해 단계별로 더 촘촘한 reward를 구성한다.
  • group rollout: 같은 초기 조건에서 여러 trajectory를 병렬로 샘플링하고, 그룹 안의 상대 성과를 정규화해 비교한다.
  • step-level advantage: 같은 시점의 행동 품질을 비교해 국소적인 credit assignment를 제공한다.
  • trajectory-level advantage: 전체 누적 보상·작업 성공을 비교해 장기 결과를 반영한다.
  • fused update: 두 advantage를 결합해, 별도 value network 없이 GRPO 계열의 clipped policy update에 사용한다.

한계와 읽을 때의 주의점

  • 현재 공개 원문은 LIBERO manipulation benchmark의 VLA post-training을 검증한다. 이동 로봇 경로 계획·다중 로봇 예약·물류 운영을 직접 다루지 않는다.
  • LLM이 만든 dense reward와 task decomposition이 잘못되면 policy도 잘못된 방향으로 최적화될 수 있다.
  • 동일 초기 조건에서 여러 rollout을 돌리는 online RL은 simulator 병렬화와 상당한 실험 예산이 필요하다.
  • 논문은 arXiv preprint이며, 실제 작업장 장기 운영·안전 인증을 검증한 논문으로 해석하면 안 된다.

Trihouse에 가져올 점

TGRPO는 지금의 Nav2 recovery manager를 대체하는 방법이 아니라 후속 VLA 연구 방법으로 유용하다. 예를 들어 “사람 발견 뒤 어떤 안전 node를 제안할까”를 VLM/VLA가 여러 개 생성하고, 단계별 안전 규칙과 전체 mission 성공·예약 충돌·복구 시간·Safety stop을 함께 보상으로 삼아 후보 생성 policy를 fine-tuning할 수 있다.

그대로 가져오면 안 되는 점

초기 PoC에서 TGRPO로 VLM을 online update하거나, LLM 보상만으로 안전 여부를 정하지 않는다. 먼저 고정 rule·Safety Supervisor·PPO recovery baseline·offline 로그 평가를 만들고, 충분한 시뮬레이터와 검증 set이 생긴 뒤에 TGRPO를 VLM/VLA의 고수준 제안 학습에만 검토한다.

PPO — 현재 정책을 조금씩, 안정적으로 개선

PPO(Proximal Policy Optimization)는 로봇이 현재 정책으로 시뮬레이터나 환경에서 rollout을 수집하고, 그 경험을 바탕으로 정책을 한 번에 너무 많이 바꾸지 않도록 제한하며 업데이트하는 actor-critic 계열 방법이다. 여기서 actor는 행동 확률을 내는 정책이고, critic은 현재 상태가 얼마나 좋은지를 추정해 보상 분산을 줄인다.

예를 들어 blocked_aisle 상태에서 PPO 정책은 WAIT 0.55, BACKOUT 0.30, REQUEST_NAV2_REPLAN 0.15처럼 복구 skill의 확률을 낸다. 시뮬레이션에서 WAIT가 안전하게 성공했다면 그 행동 확률을 올리되, clip 목적함수로 이전 정책과 지나치게 멀어지는 갱신을 막는다.

  • 장점: 학습이 비교적 안정적이고, 이산 action space와 safety constraint를 붙이기 쉽다.
  • 단점: 새 정책으로 수집한 최근 rollout을 주로 써야 하므로 샘플 효율은 SAC보다 낮다.
  • Trihouse 역할: Nav2 실패 뒤의 복구 skill 선택. PPO가 경로를 직접 만들거나 속도를 직접 명령하지는 않는다.

SAC — replay buffer를 오래 활용하는 연속 제어형 RL

SAC(Soft Actor-Critic)는 replay buffer에서 과거 경험을 반복 샘플링하는 off-policy actor-critic 방법이다. 행동 보상뿐 아니라 entropy, 즉 행동 선택의 다양성도 보상에 포함해 초기 탐색이 한 행동에 너무 빨리 고정되지 않게 한다. 두 개의 Q critic과 target network를 사용하는 구성이 대표적이다.

예를 들어 action을 안전 노드까지 후진 거리, 재관측을 위한 카메라 yaw, 후보 goal 주변의 작은 offset처럼 연속값으로 정의하면 SAC가 잘 맞는다. 반대로 WAIT/REPLAN 같은 몇 개의 이산 skill만 고르는 현재 1차 범위에서는 PPO가 더 단순하다.

  • 장점: safe/critical replay buffer를 여러 번 활용하므로 위험 사례가 비싼 실제 로봇 데이터에 표본 효율이 좋다.
  • 단점: critic 과대추정, 보상 설계, 분포가 오래된 데이터의 편향을 더 조심해야 한다.
  • Trihouse 역할: 다음 단계에서 "얼마나 후진할지" 또는 "어느 정도의 안전 offset을 줄지"를 연구할 때 후보. cmd_vel 직접 제어는 Safety/ Nav2 권한을 침범하므로 제외한다.

GRPO — 여러 VLM 후보를 서로 비교해 좋은 출력을 강화

GRPO(Group Relative Policy Optimization)는 하나의 상태 또는 prompt에 대해 여러 출력을 생성하고, 그 그룹 안에서의 상대 보상으로 advantage를 계산해 정책을 개선한다. 값 함수 critic을 별도로 크게 학습하지 않아도 그룹 내 우열을 이용할 수 있다는 점 때문에 LLM/VLM의 문장·JSON·행동 토큰 fine-tuning에 자주 논의된다.

예를 들어 같은 장면에서 VLM이 아래 세 후보를 낸다고 하자. WAIT_NODE_A1, SAFE_NODE_C2, 계속 전진. Safety rule, 예약 가능 여부, 이후 Nav2 성공 여부로 보상을 매기면, 위험 상황에서 "계속 전진"보다 검증된 안전 노드 제안을 더 높은 상대 점수로 강화할 수 있다.

  • 장점: VLM이 만들어 내는 구조화 후보를 ranking하기 좋고, 명시적인 정답 라벨이 부족한 상황에서도 결과 보상으로 정렬할 수 있다.
  • 단점: 여러 후보를 생성·평가해야 하므로 추론 비용이 든다. 또한 GRPO 자체가 Nav2 대체 주행 controller는 아니다.
  • Trihouse 역할: VLM의 위험 JSON, 안전 노드 후보, 복구 설명을 개선하는 연구용 fine-tuning 후보다.

TGRPO — 단계 점수와 전체 궤적 성공을 함께 학습

TGRPO(Trajectory-wise Group Relative Policy Optimization)는 GRPO의 그룹 상대 비교를 VLA의 실제 로봇 궤적에 맞게 확장한 방법이다. 단일 시점 출력만 잘 평가하는 것이 아니라, 각 단계의 즉시 피드백과 작업 궤적 전체의 성공·효율·안전 결과를 함께 advantage에 반영한다. 제시 논문은 실제 환경 상호작용을 활용해 VLA를 온라인 RL로 fine-tuning하는 데 초점을 둔다.

Trihouse에서는 “경로 재계획 제안이 그 순간만 안전해 보였는가”뿐 아니라, 그 선택 이후 냉동 창고 → 상온 창고 → 포장대 → 복귀 단계가 예약 충돌 없이 완료됐는지, 불필요한 후진·대기 시간이 컸는지, Safety stop이 발생했는지를 함께 평가하는 연구로 연결할 수 있다.

  • 장점: 긴 시퀀스에서 단기적으로 좋아 보이는 선택과 최종 작업 성공의 차이를 줄이는 데 적합하다.
  • 단점: 온라인 상호작용·궤적 보상·실험 인프라가 필요해 초기 PoC 난도가 높다.
  • Trihouse 역할: PPO 기반 recovery manager와 안전 로그가 안정된 뒤, VLM/VLA의 좌표·안전 노드 제안 자체를 fine-tuning하는 후속 연구다.

5. RL policy 학습이란 무엇인가

RL policy 학습은 로봇이 현재 상태를 보고 어떤 행동을 선택할지를 보상 경험으로 배우는 과정이다. policy는 보통 πθ(a | s)로 쓴다. 여기서 s는 상태(state), a는 행동(action), θ는 학습으로 바뀌는 신경망 파라미터다. 학습의 목표는 한 번의 즉시 보상만 크게 만드는 것이 아니라, 앞으로 받을 보상의 합인 return을 크게 만드는 policy를 찾는 것이다.

보상 설계의 원리

reward는 “로봇이 무엇을 중요하게 배우게 할지”를 정의한다. 잘못 설계하면 가장 가까운 길만 고르거나, 계속 멈춰서 사고를 피하는 policy가 나올 수 있다. 따라서 안전은 단순 큰 음의 보상만이 아니라 Safety Supervisor의 hard constraint로 먼저 막고, policy는 허용된 선택지 안에서 효율을 학습해야 한다.

PPO와 SAC는 이 학습 루프에서 무엇이 다른가

PPO는 최근 rollout으로 actor와 critic을 함께 업데이트한다. critic은 상태의 기대 return을 추정하고, actor는 실제 결과가 예상보다 좋았던 행동의 확률을 높인다. 이 차이가 advantage다. PPO의 clip은 업데이트 전후 행동 확률 비율이 너무 크게 바뀌는 것을 막아 학습 불안정을 줄인다.

SAC는 transition을 replay buffer에 오래 쌓고 여러 번 다시 뽑아 Q-value를 학습한다. actor는 높은 Q-value뿐 아니라 충분한 행동 다양성(entropy)도 갖도록 학습한다. 그래서 경험 재사용 효율은 좋지만, 오래된 데이터·Q 추정 오류·reward 설계를 더 엄격히 관리해야 한다.

중요: 학습(training)과 실행(inference)은 다르다. training은 시뮬레이터와 기록된 buffer로 policy 파라미터를 갱신하는 오프라인 작업이다. 실행은 고정된 검증 완료 policy가 현재 상태를 입력받아 action 하나를 고르는 일이다. Pinky가 주행 중 자신의 policy를 계속 업데이트하는 방식은 초기 범위에 넣지 않는다.

Trihouse 예외 상황 하나를 policy 학습 데이터로 바꾸면

상태 s:
  Nav2 = progress_timeout
  YOLO = person_on_path, confidence=0.94
  VLM = {risk_label: person_on_path, severity: high}
  local_costmap = path_occupied
  current_node = FREEZER_AISLE_3
  candidate_nodes = [WAIT_NODE_A1, SAFE_NODE_C2]

정책 action a:
  WAIT_AT_SAFE_NODE

환경 결과:
  Safety 승인 → Nav2가 WAIT_NODE_A1까지 이동 → 사람이 경로 이탈
  → FMS가 재계획 → 작업 재개

transition:
  (s, WAIT_AT_SAFE_NODE, 안전·재개 보상, s', done=false)

동일한 상태에서 계속 전진은 Safety가 거부하거나 위험 비용이 커서 낮은 return을 얻는다. 여러 scenario에서 이런 차이가 축적되면 policy는 사람 경로 점유 상태에서 안전 대기·재계획을 더 자주 선택하게 된다.

실제 도입의 안전한 순서

  1. Nav2 baseline과 Safety Supervisor를 먼저 고정한다.
  2. 사람·통로 차단·결로·위치 불확실성 scenario를 시뮬레이터로 만든다.
  3. 수동 설계 reward와 PPO 이산 skill policy를 학습한다.
  4. safe/critical replay와 VLM semantic label을 넣어 비교한다.
  5. offline regression과 shadow evaluation을 통과한 policy만 제한적으로 배포한다.

5. Buffer의 정확한 의미와 dual-buffer 두 안

Buffer는 “로봇이 지금 따라가는 경로”가 아니라 나중에 참조하거나 학습하기 위한 기억 저장소다. 기준 경로를 담는 buffer와 RL 학습 경험을 담는 buffer는 목적이 다르다.

구분담는 내용실시간 역할학습 역할
Route reference buffer검증된 waypoint/좌표 sequence, stage, zone, map_revision기본 경로·복귀 경로 참조복구 경로 품질 비교
Replay / learning buffer(state, action, reward, next_state)보통 직접 실행하지 않음RL policy 학습
Safe replay buffer정상 통과·안전 복구 성공 사례안전 후보 ranking안정 행동 반복 학습
Critical replay buffer사람·통로 차단·결로·Nav2 실패·위치 불확실 사례위험 상태 재확인희소 위험 사례 과대표집

1안 — Reference + Learning

검증된 기준 좌표 경로와 학습용 경험 replay를 분리한다. 운영 경로와 학습 데이터가 섞이지 않는다는 점이 장점이다. 현재 운영 기본 구조로 권장한다.

2안 — Safe + Unsafe/Critical

정상·안전 성공 사례와 위험·예외 사례를 분리한다. EE-RL처럼 rare-critical 사건을 집중 학습할 수 있다. 단, unsafe buffer는 위험 운전을 재실행하기 위한 것이 아니라, 정지·실패·근접사고·사람 개입 로그와 안전 시뮬레이터 사례를 오프라인 학습에 쓰는 저장소다.

결론: 둘 중 하나만 고르기보다 운영 = reference route buffer, 학습 = safe replay + critical replay로 결합하는 것이 가장 적합하다.
route_ref:
  map_revision, task_type, stage, waypoint_id,
  [(x, y, yaw), ...], zone, reservation_scope

replay:
  state=(pose, goal, local_costmap_summary, lidar, YOLO tracks,
         VLM risk_label, battery, Nav2_status),
  action, reward, next_state, terminated, safety_event,
  route_id, map_revision, incident_id

map_revision이 정확히 무엇인가

map_revision은 “이 좌표가 어느 버전의 지도 좌표계에서 측정됐는가”를 나타내는 불변 식별자다. 쉽게 말해 지도 파일의 버전 번호이자, 그 위에 찍어 둔 모든 (x, y, yaw) 좌표의 유효 범위를 보장하는 안전 태그다.

항목의미예시
map_name어느 공간의 지도 계열인지 나타내는 안정적인 이름trihouse_warehouse_floor1
map_revision그 지도 계열의 특정·고정된 좌표계 버전r2026-08-07-01 또는 지도 내용 hash
pose_x, pose_y, pose_yaw해당 revision의 map frame에서만 의미가 있는 위치·방향(12.40, -3.10, 1.57)

SLAM 지도를 다시 만들면 시작 원점, 벽 윤곽, scan matching 결과가 달라질 수 있다. 그러면 이전 지도에서의 (12.40, -3.10)은 새 지도에서 완전히 다른 실세계 위치를 가리킬 수 있다. map_revision 없이 과거 좌표를 실행하면 로봇이 오류를 내지 않고도 엉뚱한 곳으로 갈 수 있다.

locations 테이블 예시

작업 요청 예시
pickup_location_id: FREEZER_A
packing_station_id: PACKING_A
map_revision: r2026-08-07-01

작업을 받았을 때는 다음 세 값이 모두 일치해야 한다.

  1. 로봇이 실제로 로드한 Nav2 map의 map_name과 map_revision
  2. FMS가 작업에 붙인 map_revision
  3. 출발지·목적지·안전 노드가 저장된 locations.map_revision
불일치 규칙: 하나라도 다르면 좌표 변환이나 보정으로 억지 실행하지 않고 작업을 거절한다. 새 지도를 로드한 뒤 해당 revision으로 위치를 다시 티칭하고, 관제가 새 revision으로 작업을 다시 발행해야 한다.

revision을 올려야 하는 경우: SLAM map을 재생성했을 때, 지도 원점·스케일·방향을 바꿨을 때, 지도 파일을 교체했을 때, 또는 재티칭이 필요할 정도로 좌표계의 유효성이 변했을 때다. 반대로 사람·박스 같은 동적 장애물의 변화나 기존 지도 위에 새 location 한 개를 추가하는 일은 지도 좌표계가 같다면 revision 변경 사유가 아니다.

Trihouse DB에서는 locations에 map_name + map_revision, 좌표, location type을 보관한다. 좌표가 존재하면 map과 revision도 반드시 있어야 한다는 CHECK 제약이 이미 설계되어 있다. 로봇 launch 설정, 작업 요청, 상태 보고에도 같은 revision을 넣어야 전체 경로가 같은 지도 기준임을 증명할 수 있다.

10. Pinky-Pro 센서 융합: “한 곳에 모두 넣기”가 아니다

정확한 표현은 경로 추정이 아니라 위치 추정(localization)·장애물 인지(costmap)·경로 계획(planning)의 협업이다. Nav2는 현재 위치와 costmap을 받아 경로를 계획한다. 카메라·LiDAR·IMU·초음파는 측정 방식과 신뢰도가 다르므로 모두 EKF에 넣지 않고, 목적에 맞는 경로로 나눈다.

                  │

초음파·IRsensor_msgs/Range로 변환해 전방의 local range layer에 반영하고, 더 짧은 거리에서는 독립 Safety Supervisor가 감속/정지거리 한 개를 EKF 위치 입력으로 넣거나 Nav2만을 비상정지 장치로 간주
카메라 + YOLO/VLM초기에는 사람·통로점유·미지물체 같은 의미 위험 event를 Safety/Recovery에 전달. 카메라 내·외부 보정과 거리 추정이 끝난 뒤에만 metric obstacle 또는 landmark pose를 추가단안 RGB bbox만을 곧바로 지도 좌표 장애물로 변환하거나 VLM이 cmd_vel을 출력

좌표계(TF)가 연결의 뼈대

URDF에 고정 변환 base_footprint→lidar, →imu, →ultrasonic_*, →camera를 정확히 두고, EKF만 odom→base_footprint, AMCL만 map→odom을 발행하게 한다. 같은 TF를 두 노드가 동시에 발행하면 위치가 튀므로 금지한다. Nav2는 이 체인으로 로봇 자세를 읽는다.

카메라는 두 단계로 넣는다

  1. 1단계(권장 PoC): YOLO는 계속 실행해 사람/장애물/박스 track을 내고, 카메라 event와 LiDAR·초음파의 근접 판단을 Safety Supervisor가 결합한다. 사람은 VLM 답변을 기다리지 않고 정지·hold한다.
  2. 2단계(계측 완료 후): 카메라 intrinsic, camera↔base extrinsic, timestamp 지연을 보정한다. ArUco/AprilTag처럼 지도상 위치를 아는 마커는 PnP로 PoseWithCovarianceStamped를 만들 수 있고, RGB-D/stereo 또는 검증된 지면 투영은 장애물을 PointCloud2로 costmap에 줄 수 있다. 이때에도 느린 RTSP 원격 추론은 고속 wheel odom 대체가 아니라 드문 위치 보정으로 둔다.

현재 Pinky-Pro에 필요한 최소 연결 순서

  1. 기본 bringup에 아직 빠져 있는 IMU·ADC 거리 센서 노드를 추가하고, 실제 topic/type/rate와 frame_id를 하드웨어에서 확인한다.
  2. encoder odom + IMU로 EKF를 구성한 뒤, Nav2와 AMCL의 odom 입력을 filtered odom으로 전환한다.
  3. LiDAR는 AMCL과 기존 costmap에 유지하고, 초음파/IR은 먼저 local range layer와 별도 stop gate에만 넣는다.
  4. 카메라는 RTSP→중앙 YOLO의 지속 추론을 유지한다. metric 보정 전에는 사람·점유 event만으로 감속/정지/hold/recovery trigger를 만들고, 이후 마커 기반 pose 보정을 별도 실험한다.
현재 구현 상태: Pinky 기본 코드에는 encoder odom·RPLIDAR·AMCL/Nav2가 있지만, BNO055 IMU와 초음파·IR ADC publisher는 기본 bringup 및 Nav2 융합/costmap에 아직 연결되어 있지 않다. 그러므로 위 그림은 “현재 이미 동작 중”이 아니라 권장 통합 목표다.

근거: Nav2는 LiDAR scan으로 AMCL localization을 수행하고, costmap의 obstacle/voxel layer에는 LaserScan·PointCloud2, range layer에는 sonar·IR을 넣도록 설계되어 있다. 전역 costmap은 장기 계획, local costmap은 단기 충돌 회피에 사용된다. Nav2 Mapping & Localization · Nav2 AMCL

AMCL“도면의 여러 후보 위치 중 LiDAR 벽 모양과 가장 맞는 곳”을 계속 골라내는 탐색정적 지도 + LiDAR scan + odom 이동량으로 로봇의 map상 pose와 신뢰도를 확률적으로 계산미끄럼으로 틀어진 odom을 지도 기준으로 천천히 보정해 map→odom을 제공
costmap도면 위에 “지금 지나면 위험한 칸”을 덧칠한 실시간 위험 지도0은 통과 가능, 큰 비용은 피해야 할 곳, 치명 비용은 진입 금지. 정적 지도와 센서 관측을 겹침Planner/controller가 사람·박스·벽에 부딪히지 않으면서 좌표 시퀀스의 다음 목표로 가게 함

AMCL은 어떻게 동작하는가

  1. 처음에는 “로봇이 있을 법한 위치 후보(particle)”를 여러 개 둔다.
  2. wheel odom/IMU가 “조금 전진·회전했다”고 알려 주면 모든 후보도 그만큼 이동시킨다. 이 과정에는 미끄럼 오차를 섞는다.
  3. LiDAR scan의 벽·랙 윤곽을 정적 지도와 비교해, 잘 맞는 후보에는 높은 점수(가중치), 안 맞는 후보에는 낮은 점수를 준다.
  4. 높은 점수 후보를 많이 남기고 낮은 점수 후보를 버리는 resampling을 반복한다. 남은 후보군의 중심과 퍼짐이 현재 pose와 불확실도다.

따라서 AMCL은 카메라·초음파 자체를 기본 입력으로 쓰지 않는다. LiDAR와 지도에 강하고, 카메라는 ArUco/AprilTag처럼 정확한 pose 측정값을 만들 수 있을 때만 보조 위치 보정 후보가 된다.
