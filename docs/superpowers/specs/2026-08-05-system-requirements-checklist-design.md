# Trihouse 시스템 요구사항 체크리스트 조사 설계

작성일: 2026-08-05

## 1. 목적

Trihouse의 요구사항과 현재 구현 상태를 다음 네 책임 영역으로 나눠 조사한다.

1. Pinky-Pro 필요 기능
2. DB 필요 기능
3. 관제시스템 기능
4. 로봇팔 기능

최종 결과는 단순 요구사항 목록이 아니라 요구사항 출처, 책임 시스템, 연동 대상, 현재 구현 상태, 코드 근거, 완료 조건을 연결한 추적 가능한 체크리스트로 작성한다.

## 2. 조사 자료

요구사항은 다음 자료의 합집합으로 구성한다.

- `docs/scenario/입고_workflow.pdf`
- `docs/scenario/출고_workflow.pdf`
- `docs/scenario/비상상황_workflow.pdf`
- `docs/db_schema/trihouse_fms_schema_v3_data_dictionary.xlsx`
- `docs/setup/fms-gateway-setup.md`
- `docs/setup/system_environment/2026-08-05-vision-streaming-architecture-draft.md`
- `docs/setup/system_environment/2026-08-05-robot-arm-imitation-safe-operation-draft.md`
- `/home/newuser/Downloads/로보사피엔스_SR.pdf`의 `SR_01`~`SR_51`
- 현재 저장소의 `pinky_pro`, `control_system`, `vision_perception` 코드와 설정

SR에 없는 기능도 입고·출고·비상상황 또는 시스템 아키텍처에 필요하면 독립 요구사항으로 등록한다. SR만을 전체 요구사항의 기준으로 사용하지 않는다.

## 3. 책임 영역

### 3.1 Pinky-Pro

Pinky에서 직접 실행되어야 하는 실시간·장비·로컬 안전 기능을 담당한다.

- 모터·센서·Nav2 주행
- 로컬 장애물 회피와 안전 정지
- 작업 명령 수신, ACK, 로컬 mission 상태
- 위치·배터리·health·작업 상태 보고
- 내장 카메라 캡처와 H.264 송신
- 영상·네트워크 단절 감지와 로컬 안전 동작
- 포장대·대기 존·충전소 이동
- LED·LCD·부저와 사용자 상태 표시
- 적재·하차 하드웨어 연동

### 3.2 DB

DB는 로봇 제어 판단이 아니라 영속성, 무결성, 동시성 제어에 필요한 저장 구조를 담당한다.

- 장비·위치·재고·작업·작업 단계
- 장비 최신 상태와 heartbeat
- 작업 명령의 멱등 키와 전달 상태
- 위치·통로·장비 예약과 lock
- 사고·운영·안전 이벤트와 감사 로그
- 영상·데이터셋·모델 artifact 메타데이터
- 트랜잭션, 제약조건, 인덱스와 보존 정책

작업 배정, 경로 재계획, 비상 대응 판단은 DB 기능으로 분류하지 않는다.

### 3.3 관제시스템

FMS Gateway, 작업 오케스트레이터, 관제 UI, RTX 4060 영상 허브와 중앙 인식 worker를 포함한다.

- 입고·출고 작업 생성과 상태 머신
- 장비 배정, 우선순위, 스케줄링과 재할당
- 경로·장소·병목 예약
- 명령 발행, ACK, timeout, 재시도와 중복 방지
- 장비 상태·위치·배터리·영상 관제
- MediaMTX 영상 수신·중계·녹화
- QR·ArUco 검출과 DB 검증
- 비상구역 설정, 로봇 우회·정지·작업 보류
- 관리자 승인·정지·해제·수동 복구
- 통계·이력·관제 UI

### 3.4 로봇팔

일반 PC, OMX-AI와 RTX 5080 정책 서버로 구성된 로봇팔 실행 계층을 대상으로 한다.

- 고정캠·손목캠 캡처와 영상 송신
- QR·ArUco 및 카메라 보정 결과 사용
- 규칙 기반 관측 자세와 pre-grasp/pre-place 이동
- ACT `pick`, `place_shelf`, `place_basket`
- Action Proposal 검증과 저수준 실행
- 관절·속도·작업공간·충돌 제한과 watchdog
- 파지·배치 검증, 재시도, 안전 자세 복귀
- Pinky와 준비·인수인계 상태 동기화

현재 작업공간에는 로봇팔 구현 코드가 없으므로 로봇팔 항목은 설계 문서에 근거해 `설계됨/미구현`으로 판정한다. 실제 구현 코드가 없는 항목에 `[x] 구현`을 표시하지 않는다.

## 4. Vision/YOLO 처리 원칙

`vision_perception`은 YOLO 모델 개발 자료로 취급하며 다섯 번째 시스템 책임 영역으로 만들지 않는다.

- 데이터 수집·증강·학습 코드는 모델 개발 근거다.
- 카메라 캡처·송신 책임은 카메라가 연결된 Pinky 또는 로봇팔 일반 PC에 있다.
- inference runtime의 책임은 실제 배치 장치에 따라 관제시스템 또는 RTX 5080 로봇팔 계층에 배정한다.
- 감지 결과를 사용한 즉시 안전 정지는 Pinky 또는 로봇팔 safety supervisor가 수행한다.
- 사고 기록, 비상구역 설정과 작업 재할당은 관제시스템·DB가 담당한다.

노트북이나 증강 스크립트가 있다는 이유로 실시간 inference, 서비스 API, 사람 추적 또는 안전 제어가 구현됐다고 판정하지 않는다.

## 5. 요구사항 식별과 분해

### 5.1 식별자

- SR 원문: `SR_01`~`SR_51`
- 입고 파생: `INB-*`
- 출고 파생: `OUT-*`
- 비상상황 파생: `EMG-*`
- 영상 아키텍처 파생: `VIS-*`
- DB·데이터 파생: `DATA-*`
- 로봇팔 설계 파생: `ARM-*`

SR 하나가 여러 시스템의 동작을 포함하면 하위 요구사항으로 분해한다. 예를 들어 `SR_20 로봇 상태 공유`는 Pinky 상태 생성, 로봇팔 상태 생성, 관제 수신·stale 판정, DB 최신 상태 저장으로 나눈다. 각 하위 요구사항은 하나의 주 책임 시스템만 가진다.

### 5.2 시나리오 파생 요구사항

다음과 같이 SR에 없거나 SR보다 구체적인 시나리오 기능을 누락하지 않는다.

- 통신 장애 시 작업 ID와 마지막 완료 단계 로컬 저장
- 통신 복구 후 로봇과 관제 상태 대조 및 멱등 재개
- Pinky와 로봇팔의 준비·완료 신호 barrier
- 하차 위치 점유 확인과 안전 대기
- 현재 정지 위치에서 경로 재계획
- 우회 불가 시 안전 위치 대기
- 포장대 작업자 존재 여부와 다른 포장대 선택
- 비상구역 설정과 주변 로봇 진입 차단
- 마지막 안전 완료 단계와 물품·적재 상태 기록
- 미완료 작업의 재할당과 현장 확인 보류
- 관리자 해제 전 비상 상태 유지
- 해제 후 위치·적재·통신·센서 점검
- 스트림 단절 시 마지막 프레임 재사용 금지
- 재연결 후 새 검증 전 작업 재개 금지

## 6. 무게 기능 정책

무게 관련 기능은 삭제하지 않고 모두 `LOW` 우선순위와 `후순위`로 표시한다.

대상은 다음과 같다.

- Pinky 적재 중량 센서 또는 load cell
- 최대 적재 무게 검증
- 무게 기준 적재·하차 완료 판정
- 바구니 무게 0 여부 확인
- 카메라 결과와 무게 센서 교차 검증
- 인수인계 후 무게 기반 전달 확인
- 무게 초과 작업 분할

초기 완료 조건과 필수 통합시험에서 무게 기능은 제외한다. 1차 구현은 카메라 검증, 작업 상태 신호와 로봇팔 완료 신호를 우선 사용한다. DB의 `unit_weight_kg` 등 기존 필드는 유지하되 초기 운영의 필수 입력으로 강제하지 않는다.

## 7. 구현 상태 판정

- `[x] 구현`: 실제 실행 코드와 필요한 연결 설정이 존재한다.
- `[ ] 부분 구현`: 기반 코드가 있지만 요구된 종단 간 동작 또는 연동이 없다.
- `[ ] 미구현`: 관련 코드가 없다.
- `[?] 조사 불가`: 필요한 저장소, submodule 또는 외부 구성에 접근할 수 없다.
- `설계됨`: 구현 코드는 없지만 승인 대상 설계 문서에 구체적인 구조와 동작이 정의돼 있다.

정적 코드 확인은 하드웨어 검증 완료로 간주하지 않는다. Generic LED, Nav2 또는 카메라 모델이 있다는 이유만으로 비상 대응, FMS 연동 또는 실물 영상 스트리밍을 구현으로 판정하지 않는다.

## 8. 체크리스트 레코드 구조

각 항목은 다음 필드를 가진다.

| 필드 | 내용 |
|---|---|
| 기능 ID | 시스템별 고유 ID 또는 SR 파생 ID |
| 요구 기능 | 하나의 검증 가능한 동작 |
| 주 책임 | Pinky-Pro, DB, 관제시스템, 로봇팔 중 하나 |
| 연동 시스템 | 입력 제공자와 결과 소비자 |
| 우선순위 | P0/필수, P1/운영, P2/확장 또는 LOW/후순위 |
| 구현 상태 | 구현, 부분 구현, 미구현, 조사 불가, 설계됨 |
| 구현 근거 | 실제 파일과 주요 행 또는 설정 |
| 요구사항 출처 | SR, 시나리오, 아키텍처, DB 문서 |
| 완료 조건 | 시험으로 판정할 수 있는 합격 조건 |

구현 근거가 없는 항목에는 임의의 파일을 연결하지 않고 `관련 구현 없음`이라고 명시한다.

## 9. 문서 간 충돌 처리

모든 출처를 합집합으로 수집하되 역할은 다음과 같이 구분한다.

- SR: 상위 기능과 업무 우선순위
- 시나리오: 순서, 분기, 재시도와 예외 처리
- 시스템 아키텍처: 장치 배치, 통신 방식과 안전 제약
- DB 스키마: 저장 구조, 상태값, 무결성과 동시성 제약
- 실제 코드: 현재 구현 여부의 근거

출처 간 배치·책임·수치가 다르면 한 요구사항을 임의로 삭제하거나 덮어쓰지 않는다. `문서 간 충돌·미결정 사항` 표에 양쪽 내용을 기록하고 결정이 필요한 이유를 적는다.

## 10. 최종 산출물

최종 문서는 다음 순서로 구성한다.

1. 범위, 출처와 판정 기준
2. Pinky-Pro 체크리스트와 코드 근거
3. DB 체크리스트와 스키마·코드 근거
4. 관제시스템 체크리스트와 코드 근거
5. 로봇팔 체크리스트와 설계 근거
6. SR `01~51` 추적표
7. 시나리오·아키텍처 파생 요구사항 추적표
8. Pinky ↔ 관제 ↔ DB ↔ 로봇팔 인터페이스 표
9. 문서 간 충돌·미결정 사항
10. 입고·출고·비상상황 종단 간 커버리지 표
11. 구현 우선순위와 통합시험 순서

기존 `docs/pinky-pro-feature-checklist.md`는 이 통합 구조로 확장하거나 새 통합 문서에서 참조한다. 동일 체크리스트를 두 문서에 중복 유지하지 않는다.

## 11. 조사 전제와 제한

- `pinky_pro` submodule은 현재 코드를 조사할 수 있다.
- `control_system` submodule은 등록돼 있지만 현재 초기화되지 않아 관제 코드 판정 전에 확보해야 한다.
- 현재 작업공간에는 로봇팔 구현 코드가 없다.
- `vision_perception`에는 데이터 수집·증강 자료가 있으나 현재 확인된 범위만으로 실시간 YOLO inference 구현을 인정하지 않는다.
- MediaMTX, 배포 서비스와 외부 장비 설정은 저장소 밖 구성도 확인해야 최종 운용 상태를 판정할 수 있다.
