## 1. 목표

주문 1건이 UI/API → control_tower → 로봇까지 완주하는 것을 **시뮬(단일 로봇)에서
확정한 뒤 실기 PK_01에서 재현한다.**

두 갈래가 있고 서로 독립적이다.

- **A. 자원 회수** — 설계 8절 1~2. 잡힌 자원이 돌아오게 한다
- **B. 실기 이행** — 계획 Task 1·3·4·5·6·7. 시뮬에서 고친 것을 실기로 옮긴다

**A가 B보다 먼저다.** 지금 job 2·3이 PK_01·PK_02를 붙잡고 있어서 새 주문을 넣어도
`no free robot`으로 줄만 선다. 즉 A 없이는 **시뮬 완주 자체가 시작되지 않는다.**

## 4. 반드시 알아야 할 사실 — 시뮬과 실기는 다른 nav2 스택이다

|  | 시뮬 | 실기 |
|---|---|---|
| launch | `nav2_bringup` (Jazzy 표준) | 벤더 `pinky_navigation/launch/bringup_launch.xml` |
| lifecycle 노드 | 11개 | **6개** (collision_monitor·docking_server·route_server 없음) |
| params 적용 | `RewrittenYaml(root_key=namespace)`가 감싸 줌 | **`<param from>`으로 원본 그대로** |
| `/cmd_vel` 발행자 | `collision_monitor` | `velocity_smoother` |

**시뮬에서 고친 5개 중 실기로 옮겨야 하는 건 2개뿐이다** — TF namespace, params root
key. collision_monitor·docking_server 절 보충은 실기가 그 노드를 안 띄우므로 해당 없다.

그런데 실기 벤더 XML도 `<remap from="/tf" to="tf"/>`를 똑같이 걸고
`<push-ros-namespace>`를 적용한다. 그래서 **TF 분리로 AMCL이 스캔을 전량 폐기하는
실패는 실기에서 그대로 재현된다.** 벤더 params 최상위 키는 `amcl:`,
`controller_server:` 같은 맨 이름이고 `/**:` 와일드카드가 없어 `/pinky_01/amcl`과
매칭되지 않는다.

`pinky_pro`는 보호 경로다. 벤더 파일을 고치지 말고 우리 저장소의 인자와 파생
params로 우회한다 — 계획 Task 4·5가 그 방법이다.

### 분기점 (계획 Task 3)

로봇에서 벤더 bringup에 `<arg name="namespace">`와 `<push-ros-namespace>`가 둘 다
있는지 본다.

- **A**: 둘 다 있음 → 계획 Task 4·5를 한다
- **B**: 하나라도 없음 → 단일 로봇을 `namespace:=''`로 띄운다. nav2가 루트에 있으니
  벤더 params 맨 키가 그대로 맞고 `/tf` remap도 루트로 해석되어 **두 문제가 동시에
  사라진다.** Task 4·5를 건너뛴다. 대신 2대 운용은 다음 날

## 5. 시작 전에 결정이 필요한 것

**설계 4.6(이상 보고)을 오늘 넣을 것인가.** 설계 10절이 스스로 확인한 공백이 있다.

- `incidents` 테이블은 있다
- **Gateway에 incidents API가 없다**
- 관제 UI는 incidents를 **읽기 전용**으로만 보여 준다. 승인을 보낼 경로가 없다

4.6은 "사람이 `acknowledged`로 바꾸기 전까지 그 job은 다시 배정되지 않는다"고 정한다.
승인 경로 없이 incident만 열면 **아무도 닫지 못해 job이 영구히 멈춘다** — 지금 job
2·3이 자원을 붙잡은 것과 **같은 종류의 교착을 새로 만드는 셈**이다.

선택지는 둘이다.

1. **오늘은 4.6을 넣지 않는다** (권장). 8절 1~2만 하고, 만료는 조용히 회수하며
   `operation_event`만 남긴다. 실기 이행에 집중한다
2. 4.6과 함께 `GET /api/v1/incidents?state=open`, `POST /api/v1/incidents/{id}/acknowledge`,
   UI 승인 버튼까지 한 번에 만든다. 하루 안에 실기까지 가기는 어려워진다

**설계가 경고한 대로, 실기 이행 전에는 이 경로가 관제 화면에 실제로 뜨는지 사람이
확인해야 한다.** 즉 선택 1을 택하면 "실기에서 자동 만료 회수가 도는 상태로 로봇을
움직인다"는 뜻이므로, 실기 시험 중에는 만료 회수 호출을 끄거나 여유(`RESERVATION_GRACE`)를
넉넉히 두는 편이 안전하다. **어느 쪽으로 갈지 나에게 물어라.**

## 6. 절대 규칙

- **`pinky_pro/**`, `control_system/**`는 읽기·실행만.** 어떤 태스크도 그 아래를
  수정하지 않는다.
- **로봇팔(OMX)은 다른 팀원 담당.** `trihouse_omx_adapter/**`,
  `control_tower/task_manager/omx_*`, `control_tower/gateway/omx_*`를 건드리지 않는다.
- **카메라는 ROS를 거치지 않는다.** 로봇의 `camera_streamer`가 ffmpeg로
  MediaMTX(PC1)에 RTSP push하고, 서버가 `vision_edge/perception.py`의
  `cv2.QRCodeDetector`·`cv2.aruco.DICT_5X5_50`으로 인식한다. **카메라 토픽을 ROS
  브리지에 추가하지 마라.** 이건 우회가 아니라 원래 설계다.
- **도메인: 시뮬 0, 실기 52.** 절대 섞지 않는다.
- **로봇 선택은 robot_id 기준** — `robots:=PK_01`, `TRIHOUSE_ROBOTS=PK_01`.
  namespace(`pinky_01`)가 아니다.
- **스키마는 바꾸지 않는다.** 설계 5절이 "쓰는 방식만 바뀐다"고 못박았다.
- **TDD로 간다.** 실패하는 테스트 먼저 → RED 확인 → 최소 구현 → GREEN 확인 → 커밋.
  계획 문서에 각 태스크의 실제 테스트 코드가 들어 있고, 설계 8절에는 단계마다 검증
  방법이 붙어 있다.

## 7. 함정 (직전 세션들이 실제로 밟은 것들)

- **`pkill -f <패턴>`을 직접 쓰지 마라.** 패턴이 자기 명령줄에 들어가 자멸하고
  Docker 컨테이너의 ROS 프로세스까지 죽인다. `scripts/sim_teardown.sh`를 써라.
- **브링업 완료 전에 측정하지 마라.** `Managed nodes are active` 개수가 기대치와
  같아진 뒤에 재라. 직전 세션이 이걸 세 번 이상 반복했다.
- **`ros2 topic echo`/`topic list`/`param get`을 쓰지 마라.** 그래프 열거에 의존해
  부하가 높으면 40초 timeout으로 멈춘다. 확인은 `scripts/verify_robot_status.py`로 한다.
- **pytest는 항상** `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 .venv/bin/pytest`. 안 그러면
  `launch_testing` 플러그인이 venv pytest와 충돌해 `PluginValidationError`가 난다.
- **`PYTHONPATH`는 덮어쓰지 말고 더해라** (`"...:$PYTHONPATH"`). 덮어쓰면
  `ModuleNotFoundError: rclpy`.
- **`status_node`를 고치면 재빌드해야 한다** — install이 복사본이다.
  `colcon build --packages-select trihouse_pinky_fleet --symlink-install`.
  launch 파일은 symlink라 재빌드가 필요 없다.
- **ROS 명령 전 3단 source**: `/opt/ros/jazzy/setup.bash` → `install/setup.bash`
  → `pinky_pro/install/setup.bash`.
- **`EDGE_BIND_ADDRESS`는 Ethernet 쪽 주소여야 한다.** Wi-Fi 쪽에 바인딩하면 로봇이
  못 붙는 동시에 8554가 바깥으로 노출된다. 서버 PC는 인터페이스가 둘이다.
- **MySQL이 셋 나란히 뜬다.** `trihouse-mysql`(3308, 실기동/개발 `trihouse_fms` — Gateway가
  쓴다), `trihouse_db-mysql-1`(3306, 보존 개발), `trihouse_db_test-mysql_test-1`(3307,
  tmpfs 테스트). 헷갈리면 엉뚱한 DB를 고친다.

## 8. 실패를 판정하는 법

시뮬 lifecycle bringup은 **부하로 간헐 실패한다.** 12코어에 로봇 2대면 load
average가 60~130까지 오르고 lifecycle manager가 `map_server/get_state`를 기다리다
포기한다. 코드 결함이 아니다.

- 실패하면 `uptime`을 **먼저** 본다. load average가 60을 넘으면 그 실패는 버그로
  판정하지 마라 — 이 상태의 timeout은 실제 결함과 구분되지 않는다.
- **단, `robots:=PK_01`로 한 대만 띄웠는데도 실패하면 그건 부하가 아니라 남은
  버그다.** systematic-debugging으로 근본 원인을 찾아라.
- 실기에는 Gazebo도 두 번째 로봇도 없으므로 이 부하 문제 자체가 없다. **실기에서
  실패하면 처음부터 실제 결함이다.**

## 9. 나에게 물어야 하는 것

- **5절의 결정** — 설계 4.6(이상 보고)을 오늘 넣을지
- **운영 DB(`trihouse_fms`) 쓰기** — job 2·3 취소를 실제로 실행하기 전에. 새로
  만든 취소 엔드포인트를 쓰더라도 되돌릴 수 없는 쓰기다
- `pinky_pro` 변경이 필요해 보일 때 (보호 경로)
- 시뮬 Gazebo 카메라(1280×720@30 `always_on`, 아무도 안 쓰는데 GPU 없이 소프트웨어
  렌더링 중)를 끌지 — `pinky_gz.urdf.xacro`가 보호 경로 안이라 승인이 필요하다
- 계획 Task 1에서 단일 로봇으로 3회 연속 실패할 때
- 실기 map 파일 경로, 승인된 `map_revision`, 관제 호스트 Ethernet IP
- 설계 9절의 열린 질문 — 공칭 속도의 정본, 로봇 현재 위치의 출발점. **다만 이 둘은
  ETA(8절 5번 이후) 이야기이므로 오늘은 답이 필요 없다**

## 10. 범위 밖 (오늘 하지 않는다)

- 로봇팔 물리 동작 (다른 팀원)
- 설계 8절 5~10 — ETA 추정기, ETA 최소화 할당, `time_slot` 전방 예약, `in_use` 전이,
  실제 경로 기반 ETA. 단일 로봇에서는 first-fit과 결과가 같다
- 설계 6절이 명시적으로 뺀 것 — 선점, 혼잡 반영 재계획, 다중 창고·다중 층,
  시간대별 인력 계획
- RMF 낙찰 기반 할당(SR07)·긴급 비선점(SR41)·안전 재할당(SR08). **할당 주체는
  control_tower다** — 이 시스템은 로봇을 지정해서 RMF에 넘기고 RMF가 다른 로봇을
  배정하면 `ASSIGNMENT_MISMATCH`로 거부한다. 로봇 말고 팔·Dock·충전기도 함께
  배정해야 하므로 그 경계가 맞다
- 2대 동시 운용. `path_schedule.py` 연결이 선행되어야 한다 — 두 로봇이 동시에
  stubborn override를 쥐지 못하게 하는 안전 장치인데 지금 어느 실행 경로에도 없다
