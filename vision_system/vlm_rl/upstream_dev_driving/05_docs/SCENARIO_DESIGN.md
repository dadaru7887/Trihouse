# 시나리오 설계 + 데이터 수집 가이드라인

## 시설 레이아웃 (2026-08-14 사진 기준)

```
[충전소]──────────────────────┐
(왼쪽 위, 검은 띠)              │
   │                          [상온](빨강)
   │  (열린 바닥, ArUco         [냉장](노랑)
   │   waypoint 마커들)         [냉동](초록)
   │                              │
   └──────────────[전달대]────────┘
                (하얀 걸상 모양,
                 카메라 장착됨)
```

- **충전소(시작점)** → **상온/냉장/냉동 중 필요한 곳(적재)** → **전달대(배송)** → 충전소 복귀
- **정적 장애물**: 파란 기둥 모양
- **동적 장애물**: 사람 모형/레고(이동)

## 비상상황(실패/충돌로 이어지는 것) 데이터 우선순위

**왜 "아무 위험 상황"이 아니라 실제 실패/충돌로 이어지는 상황을 우선해야 하는가**: TGRPO는
같은 state에서 시도된 여러 skill의 reward를 비교해서 배움(group-relative advantage). **여러
skill을 시도했는데 결과가 다 거기서 거기(전부 안전 or 전부 위험)면 advantage가 0에 가까워서
사실상 배울 게 없음** — 오늘 추가한 DAPO dynamic sampling은 이런 경우 아예 업데이트를
스킵하게 만들어놨을 정도로(`04_training/offline_train_from_buffer.py`), "결과가 갈리는"
데이터가 진짜 값어치 있음. 즉 우리가 원하는 건 "위험한 상황" 자체가 아니라 **"어떤 대응을
했느냐에 따라 결과가 실제로 갈리는 상황"**임.

**솔직히 말씀드리면**: 어떤 셋업이 실제로 충돌/CRITICAL로 이어질지는 저희도 미리 100%
장담 못 함(그래서 buffer가 지금 CRITICAL 1개뿐인 것도 "일부러 안 만들어서"라기보다 "만들기
어려워서"에 가까움). 대신 **오늘 실측으로 이미 확인된, 실패 확률이 높은 조건들**을 활용하면
"찍어서 맞히기"보다 훨씬 승률이 높음:

1. **비대칭 footprint의 회전 반경 문제** — 오늘 냉동구역 코너에서 실측: 로봇이 폭 15cm 안팎인
   틈을 대각선으로 진입/회전해야 하는 상황에서 반복적으로 collision 직전까지 감(RPP
   circumscribed radius 11.7cm 이슈). **좁은 틈 + 회전이 동시에 필요한 셋업**이 지금까지
   확인된 것 중 실패 유도가 제일 잘 됨.
2. **LiDAR 위험거리(0.085m) 문턱 근처** — `is_terminal_critical()`이 이 값을 기준으로
   판정함. 장애물을 로봇 진행 방향 정면 10~15cm 안쪽까지 들어오게 세팅하면(사람이 실제로
   다치지 않을 안전거리는 유지하면서) CRITICAL 판정이 상대적으로 잘 나옴.
3. **회피 공간이 비대칭인 상황** — 왼쪽은 넓고 오른쪽은 좁은데 장애물이 애매하게 중앙에
   있는 경우. REROUTE_LEFT/RIGHT 중 하나는 성공, 하나는 실패할 가능성이 커서 skill 간
   reward 차이(=학습 신호)가 크게 남.
4. **정적+동적 중첩**(위 스토리 6번) — 정적 장애물 회피 경로 위에 동적 장애물이 겹치면,
   "정적만 있을 때 최선이었던 경로"가 더 이상 최선이 아니게 됨 -- 같은 state라도 타이밍에
   따라 다른 skill이 정답이 되는 케이스라 데이터 가치가 높음.

**우선순위가 낮은(굳이 더 안 모아도 되는) 경우**: 장애물이 아예 없거나 명백히 멀리 있어서
어떤 skill을 골라도 결과가 똑같이 안전한 상황(위 스토리 8번 "잠깐 스쳐가는 장애물"과는
다름 -- 8번은 "트리거 오탐 여부"를 보는 거라 목적이 다름). 이런 건 이미 SAFE 버킷이
충분하면(현재 8개) 우선순위를 낮춰도 됨.

**안전 수칙**: 실제 충돌 직전까지 유도하는 거라 사람에게는 절대 안 함(마네킹/레고/기둥
모형만 사용), 항상 사람이 옆에서 Enter 확인 단계를 거치게 하고, `terminal_critical`
문턱(0.085m)보다 한참 여유 있게 시작해서 점진적으로 좁혀가는 방식 추천(오늘 급하게
좁히다가 실제로 부딪힌 사고가 있었음 -- 매핑 노이즈+footprint 문제였지만, 점진적 접근이
더 안전함).

## 운행 중 데이터 수집 체크리스트 (실제 조작하시는 분용)

로봇 운행하시면서 아래 8가지 상황을 **의도적으로 한 번씩은 겪게 만들어주세요.** 그냥 아무
장애물 없이 왕복만 반복하면 데이터가 죄다 "쉬운 케이스"로만 쌓여서, 나중에 정작 위험한
순간엔 로봇이 뭘 해야 할지 학습이 안 됩니다.

**진행 방법**:
1. 아래 8개 상황 각각 **최소 3번씩** 겪게 해주세요 (한 번만으로는 우연인지 아닌지 알 수 없음).
2. `orchestrate_live_teleop.py --execute` 모드로 실행 중이어야 실제로 학습 데이터가
   쌓입니다 -- 그냥 teleop만 하고 있으면 "관찰"로만 기록되고 학습엔 안 씀.
3. 로봇이 스스로 판단해서 움직이려고 할 때(recovery 실행 직전) "손 떼고 Enter 확인" 창이
   뜨는데, **위험해 보이면 Enter 안 누르고 그냥 관찰만 하셔도 됩니다** -- 그것도 유효한 데이터임.
4. 각 상황 겪을 때마다 대충 몇 시(분)에 몇 번 상황을 시도했는지 메모만 남겨주세요(엑셀/메모장
   아무거나) -- 나중에 로그랑 대조할 때 필요함. 정식 시나리오 태그 필드는 아직 코드에 없어서
   (`recovery_data_collector.py`에 `scenario_id` 추가하는 게 다음 작업 후보), 지금은 사람이
   수동으로 기록하는 수밖에 없음.
5. 영상/사진도 같이 남겨주시면 좋습니다(`evidence_pipeline.mp4`처럼) -- 나중에 "왜 이런
   판단을 했는지" 눈으로 재확인할 때 큰 도움됨.

## 스토리형 시나리오 (현장에서 바로 재현용)

표로만 보면 감이 안 오니, 실제로 사람이 재현할 수 있는 상황극 형태로 정리. 각 시나리오
끝에 "확인 포인트"를 달아서 뭘 보려고 이 상황을 만드는지 명확히 함.

### 1. 배송 중 갑자기 사람이 튀어나옴
충전소에서 나와 냉장구역에서 물건을 픽은 뒤 전달대로 이동 중, 선반 뒤에 숨어있던 사람이
경로 위로 갑자기 걸어나옴(정적 장애물 뒤에서 동적 장애물이 순간 등장하는 조합).
- **확인 포인트**: `신규_출현_확정` 트리거가 몇 프레임 만에 잡는지(`CONFIRM_FRAMES=3`,
  0.6초), `dynamic_obstacle_predictor.py`가 사람의 이동 방향을 제대로 외삽하는지.

### 2. 쓰러진 사람 발견 ⚠️ 현재 미구현 영역
경로 위에 사람이 서있지 않고 바닥에 누워있음(다친 상황을 흉내).
- **확인 포인트**: 지금 세그멘테이션은 "person" 클래스 하나뿐이라 **서있는 사람과 쓰러진
  사람을 구분 못함** — 똑같이 "장애물 회피"로만 처리될 가능성이 높음. 이 시나리오는 "된다"를
  확인하는 게 아니라 **"안 되는 걸 직접 눈으로 확인"하는 용도**임(2026-08-13 기록에도
  "쓰러진 사람 감지는 완전히 별개 레이어 문제, 아직 논의만 함"으로 남아있던 항목). 여기서
  나온 영상/로그는 나중에 "쓰러진 사람=회피 대상이 아니라 정지+알림 대상"으로 별도 분류
  레이어를 설계할 때 참고자료로 씀.

### 3. 마주오는 사람과 좁은 통로에서 만남
병목(bottleneck) 구간에서 반대편에서 사람이 걸어옴 — 로봇도 사람도 서로 피해야 하는 상황.
- **확인 포인트**: REROUTE_LEFT/RIGHT 중 어느 쪽을 고르는지 일관성 있는지(예: 항상 오른쪽
  회피처럼 사람이 예측 가능한 패턴을 보이는지), 병목 특성상 회피 공간 자체가 좁아서
  `terminal_critical` 문턱(0.085m)에 걸릴 위험이 큼 -- 오늘 냉동구역 코너 이슈랑 같은 계열.

### 4. 물건 픽업 직후, 몸을 돌리는 순간 장애물 등장
냉동구역에서 물건을 집고 방향을 트는(회전) 바로 그 타이밍에 옆에서 장애물이 나타남 -- "이미
움직이기 시작한 상태에서" 트리거가 걸리는 케이스.
- **확인 포인트**: 회전 중 트리거 반응 지연이 실제 위험으로 이어지는지(2026-08-11 분석
  기준 "회전/정지 중 지연은 물리적 위험 거의 없음"이었는데, 이 결론이 오늘도 유효한지 재확인).

### 5. 장애물이 로봇 쪽으로 빠르게 돌진
사람(또는 레고)이 로봇을 향해 빠르게 다가옴 -- 세그멘테이션 신뢰도 확정을 기다릴 여유가
없는 상황.
- **확인 포인트**: `거리_위험`(LiDAR 기반, 세그멘테이션과 무관하게 danger zone 진입 즉시
  발동) 안전판이 실제로 `신규_출현_확정`보다 먼저 반응하는지 -- 이게 최후의 안전 백스톱임.

### 6. 배송 도중 배터리가 위급 상태로 떨어짐
정상 배송 중간에 배터리가 CRITICAL 임계값 아래로 떨어짐(시뮬레이션상 강제 트리거 또는
실제 방전).
- **확인 포인트**: 이 상황에서 VLM/RL 파이프라인이 아예 안 끼어들고 `battery_watcher.py`의
  결정론적 규칙(가장 가까운 safe_zone/충전 가능 지점으로)이 곧바로 우선하는지 -- "배터리
  같은 안전필수 상황은 학습 중인 정책에 맡기지 않는다"는 설계 원칙 자체를 검증하는 시나리오.

### 7. 전달대 코앞에서 마지막 순간 막힘
목적지(전달대) 바로 앞, 거의 다 온 상태에서 갑자기 장애물이 나타남.
- **확인 포인트**: `MISSION_REJOINED_THRESHOLD_M`(0.15m)이랑 `clearance_cost` 기준거리(0.3m)가
  실제로 목적지 근처의 좁은 공간에서 합리적으로 작동하는지 -- 목적지 근처는 원래 접근이
  타이트한 구간이라 다른 구간보다 오탐/오차가 더 클 수 있음.

### 8. 잠깐 스쳐 지나가고 사라지는 장애물 (오탐 유도)
사람이 로봇 경로를 잠깐 가로질렀다가 바로 원래 자리로 돌아가서, 실제로는 회피가 전혀 필요
없었던 상황.
- **확인 포인트**: 트리거가 과민반응해서 불필요한 recovery를 실행하는지(`VLM_COOLDOWN_SEC`,
  `CONFIRM_FRAMES` 튜닝이 이런 순간적 이벤트에 대해 여전히 적절한지) -- 이건 "잘 회피했다"가
  아니라 "애초에 회피할 필요가 없었는데 했는지"를 보는 케이스라 위 표의 버킷 분류만으론
  안 잡힘(reward가 좋게 나와도 "불필요한 개입"일 수 있음, 이 부분은 로그를 사람이 직접
  다시 봐야 함).

## 시나리오 매트릭스 (파라미터 조합용 요약)

**중요: "성공/실패"를 사람이 미리 정하는 게 아님.** buffer는 실행 결과를 `compute_real_reward()`가
계산한 **reward(연속값)** + `terminal_critical`(충돌/비상/사람개입 시 True인 플래그)만 저장하고,
`BucketedReplaySampler`가 그걸로 **자동** 분류함:
- `terminal_critical=True` → **CRITICAL**
- 안 critical인데 `reward < 0.2`(margin) → **BOUNDARY**
- 그 외 → **SAFE**

즉 아래 "예상 경향" 컬럼은 시나리오를 짤 때 "이런 상황이면 대충 이 버킷에 떨어지겠지"라는
**예측**일 뿐, 실행 전에 강제로 라벨링하는 게 아님 — 실제로는 실행해봐야 어느 버킷인지 앎.
아래는 "가능한 조합"이 아니라 **버킷 다양성 확보에 필요한 최소 세트**로 추린 것.

| ID | 주문(적재) | 장애물 종류 | 장애물 위치 | 예상 경향(실행해봐야 확정) | 이게 스트레스 테스트하는 것 |
|---|---|---|---|---|---|
| S1 | 냉동(초록) | 없음 | - | SAFE 쪽 | 트리거 자체가 안 뜨는 정상 케이스 -- 오탐(false trigger) 있는지 확인용 |
| S2 | 냉장(노랑) | 정적(파란 기둥) | 경로 위, 정면 | SAFE~BOUNDARY | REROUTE_LEFT/RIGHT 중 뭘 고르는지, 6C-Lite survivor 판정 |
| S3 | 상온(빨강) | 정적(파란 기둥) | 경로 옆, 스칠 듯 | BOUNDARY 근처 | 좁은 틈 판단 -- 오늘 냉동구역 코너에서 겪은 것과 같은 종류 |
| S4 | 냉동(초록) | 동적(사람/레고) | 경로를 가로질러 이동 | SAFE~BOUNDARY | tracking 트리거, `dynamic_obstacle_predictor.py`(선형 외삽) 실측 |
| S5 | 냉장(노랑) | 동적 | 접근하다가 멈춤(정적으로 전환) | BOUNDARY | "움직이다 멈춘 물체"를 여전히 동적으로 오판하는지 확인 |
| S6 | 상온(빨강) | 정적+동적 동시 | 정적 장애물 회피 중 동적 장애물 등장 | **CRITICAL 유도** | 복합 상황에서 안전필터(R0-06 인간감독)가 실제로 개입하는지 확인 |
| S7 | 냉동(초록) | 정적(파란 기둥) | 배송지(전달대) 바로 앞 | BOUNDARY~CRITICAL | 목적지 근처 좁은 접근 -- goal_pos 근처 clearance_cost 실측 |
| S8 | (무작위) | 없음 | - | 해당없음(배터리 override는 VLM/RL 자체를 안 거침) | `battery_watcher.py` 우회 로직 검증(설계 원칙 확인용) |
| S9 | 냉장(노랑) | 정적(파란 기둥) | 경로 위 | 실행 자체가 human veto로 막힘 | R0-06 human-in-the-loop 안전판이 실제로 막는지(2026-08-11 밤 검증 방식과 동일) |
| S10 | 냉동(초록) | 동적(사람/레고) | 로봇 쪽으로 빠르게 접근 | **CRITICAL 유도** | `거리_위험` 트리거(세그멘테이션 무관 안전판)가 실제로 뜨는지, 응답 지연 확인 |

## 왜 "위험한 상황"을 일부러 넣는가

- buffer가 지금 CRITICAL 사례 1개뿐이라(2026-08-12 실측), 목표비율(20%)을 못 채워서 학습 신호가
  약함 — S6/S10처럼 **의도적으로 위험한 상황을 만들어서** CRITICAL/BOUNDARY 데이터를 늘려야 함.
- SAFE 케이스만 모으면 정책이 "항상 되는 상황"만 학습해서, 실제로 위험할 때 어떻게 해야
  하는지 신호가 없음(회피가 아니라 정지/후퇴를 배워야 하는 경우도 있어야 함).
- **S9는 좀 다른 케이스**: buffer에 아예 안 남을 수도 있음(사람이 Enter 안 누르면
  `is_execution=False`로만 기록되거나 기록 자체가 스킵될 수 있음, `nav_recovery_executor.py`
  실제 호출부 확인 필요) — 이건 reward 버킷 문제가 아니라 "안전판이 작동하는지" 자체를 눈으로
  확인하는 용도.

## 데이터 수집 진행 가이드

1. **한 시나리오당 최소 3회 반복** — 같은 셋업이어도 VLM 판단/RL 후보가 매번 다르게 나올 수
   있어서(특히 미학습 정책은 거의 무작위), 1회만으로는 그 시나리오의 "전형적 결과"를 알 수 없음.
2. **`orchestrate_live_teleop.py --execute`로 실행** — teleop 관찰(`is_execution=False`)은
   학습에 안 쓰이니, 실제로 배울 데이터를 모으려면 반드시 `--execute`로 Nav2가 실제 실행하게
   해야 함(사람 감독 하에 Enter 확인).
3. **각 회차마다 `meta`에 시나리오 ID를 남기는 게 좋음** — 지금 buffer 구조엔 시나리오 태그가
   없어서, 나중에 "S6 케이스만 모아서 보기"가 안 됨. `recovery_data_collector.py`에
   `scenario_id` 필드 추가하는 걸 다음 작업으로 고려(간단한 추가, 오늘은 안 함).
4. **CSV/영상 증거를 실행마다 남길 것** — `evidence_pipeline.mp4`처럼 단계별 캡처를 자동화한
   패턴이 이미 있음(`capture_full_vlm_rl_evidence.py`), 시나리오별로 이 캡처를 남겨두면
   나중에 "왜 이 transition이 이런 reward를 받았는지" 사람이 눈으로 재확인 가능.
5. **목표량**: `offline_train_from_buffer.py`의 `MIN_TRANSITIONS_TO_TRAIN=4`는 "죽지 않고
   도는" 최소치일 뿐, 의미 있는 학습엔 한참 부족. 위 10개 시나리오 × 3회 = 최소 30개
   execution transition을 1차 목표로 잡는 게 현실적(지금 SAFE 8/BOUNDARY 22/CRITICAL 1과
   비슷한 규모를 시나리오별로 고르게 분산시키는 방향).
