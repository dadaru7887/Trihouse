## 1. 왜 셋인가

같은 화면에서 같은 로봇을 봅니다. 그런데 그 숫자가 어디서 왔는지는 셋 중
하나입니다.

| | 무엇 | 언제 쓰나 |
|---|------|-----------|
| 🔬 **앱 Mock** | 앱이 제 안에서 계산 | 화면·배차 규칙을 짤 때. 아무것도 안 띄워도 됨 |
| 🧊 **Gazebo 시뮬레이션** | 물리 엔진이 굴리고 토픽으로 옴 | 로봇 없이 실제와 같은 얼개를 시험할 때 |
| 🤖 **실제 로봇** | 진짜 모터·라이다에서 옴 | 현장 |

**로봇마다 따로 정합니다.** 실물 두 대를 돌리면서 한 대만 Gazebo로 시험하는 일이
흔합니다. 화면 전체에 하나로 두면 그런 구성을 담을 수 없습니다.

> **기본값은 Mock입니다.** 등록만 하고 아무것도 안 고른 로봇을 실행에 밀어 넣으면
> 안 됩니다.

---

## 2. 무엇이 같고 무엇이 다른가

**위쪽은 셋 다 같습니다. 맨 아래 한 겹만 다릅니다.**

```
          작업 지시 (앱 · rmf-web)
                  ↓
          RMF 배차 · 교통 정리                ← 셋 다 같음
                  ↓
    ┌─────────────┼─────────────┐
    ↓             ↓             ↓
 앱이 계산     Nav2 + AMCL   Nav2 + AMCL      ← Mock 만 다름
    ↓             ↓             ↓
   없음      Gazebo 물리    진짜 모터         ← 여기만 바뀜
```

토픽 이름과 형식도 **Gazebo와 실물이 같습니다.** 그래야 위쪽이 그대로 돕니다.

| 토픽 | 형식 | Mock | Gazebo | 실물 |
|------|------|:----:|:------:|:----:|
| `/<로봇>/odom` | `nav_msgs/Odometry` | ✗ | ✓ | ✓ |
| `/<로봇>/scan` | `sensor_msgs/LaserScan` | ✗ | ✓ | ✓ |
| `/<로봇>/camera/image_raw` | `sensor_msgs/Image` | ✗ | ✓ | ✓ |
| `/<로봇>/imu_raw` | `sensor_msgs/Imu` | ✗ | ✓ | ✓ |
| `/<로봇>/joint_states` | `sensor_msgs/JointState` | ✗ | ✓ | ✓ |
| `/<로봇>/cmd_vel` → | `geometry_msgs/Twist` | ✗ | ✓ | ✓ |

**Mock만 하나도 없습니다.** 앱 안에만 있는 로봇이라 주고받을 상대가 없습니다.

## 3. ① 앱 Mock — 아무것도 안 띄워도 됩니다

### 스폰

```
로봇 등록 → 값의 출처: 앱 Mock → 로봇 Spawn
```

지도 위에 로봇이 나타납니다. Gazebo도 RMF도 안 뜹니다.

### 작업을 시키면

앱이 직접 굴립니다.

1. 작업을 만들면 앱이 Waypoint 순서로 경로를 풉니다
2. 앱의 타이머가 로봇을 그 경로 위로 조금씩 옮깁니다
3. 배터리도 앱이 줄입니다
4. 지점에 닿으면 다음 단계로 넘어갑니다

**물리가 없습니다.** 벽을 통과하지도, 미끄러지지도, 밀리지도 않습니다. 로봇이
서로 부딪히지도 않습니다.

### 로봇 상세에서 보이는 것

```
🔬 앱 Mock 데이터
   앱이 계산한 값입니다.

주고받는 토픽
   앱 Mock 로봇은 토픽을 쓰지 않습니다.
   앱이 제 안에서 굴리는 로봇이라 주고받을 상대가 없습니다.
```

라이다·카메라 칸이 아예 나오지 않습니다. 없는 것을 빈 자리로 두면 오다가 끊긴
것처럼 보입니다.

### 무엇을 확인할 수 있나

- 화면·목록·배차 규칙
- 작업 단계가 순서대로 넘어가는가
- 여러 대에 일을 나눠 주는 규칙

### 무엇을 확인할 수 없나

- 실제로 그 길을 갈 수 있는가
- 좁은 통로에서 부딪히지 않는가
- 센서가 무엇을 보는가

## 4. ② Gazebo 시뮬레이션 — 로봇 없이 실제와 같은 얼개

### 스폰

```
로봇 등록 → 값의 출처: Gazebo 시뮬레이션 → 자리(충전/설비 Waypoint) 고르기
로봇 → 자리 맞추기 로 좌표 확인
Open-RMF 백엔드 띄우기
```

백엔드가 뜨면 이 순서로 올라갑니다.

```
run_<맵>.sh
├── 월드에 센서 시스템을 채운다        ← 없으면 라이다가 아예 안 돈다
├── <맵>_bringup.launch.xml
│   ├── Gazebo (헤드리스 렌더링)
│   ├── robots/<ID>/spawn.launch.xml   ← 로봇마다 하나씩
│   │   ├── robot_description.sh       ← 벤더 xacro 를 손봐서 URDF 를 만든다
│   │   ├── robot_state_publisher
│   │   └── ros_gz_sim create          ← 자리 맞추기의 좌표로 올린다
│   └── ros_gz_bridge                  ← 절대 이름으로 로봇마다 가른다
└── <맵>.launch.xml
    ├── RMF core (교통 일정·배차·건물 맵)
    └── fleet adapter
```

**로봇을 올린 자리가 곧 RMF 좌표입니다.** 홈1에 등록하면 Gazebo의 (1.761, −0.638)에
섭니다 — [좌표계](COORDINATE_FRAMES.md)를 보세요.

### 실제로 측정한 값

```
/clock                       99.994 Hz   (RTF 1.0005)
/pinky_01/odom               48.8 Hz
/pinky_01/scan                9.7 Hz
/pinky_01/camera/image_raw   30.7 Hz
map → pinky_01/base_footprint  [1.761, −0.638, 0.000]   ← 홈1 그대로
```

라이다가 재는 값도 실제입니다.

```
ranges: 0.395  0.416  0.380  0.411  0.391 ...   ← 앞의 벽까지 0.4m
```

### 작업을 시키면

Nav2가 몹니다. 앱이 아닙니다.

1. RMF가 어느 로봇에 맡길지 **입찰**로 정합니다
2. 어댑터가 목적지를 Nav2의 `NavigateToPose`로 바꿉니다
3. Nav2가 지도와 라이다로 길을 만들고 `cmd_vel`을 냅니다
4. Gazebo가 그 명령대로 바퀴를 굴립니다
5. AMCL이 라이다로 위치를 잡아 `map → odom`을 냅니다
6. 어댑터가 그 위치를 RMF에 되돌립니다

**벽이 있으면 못 갑니다. 밀리고 미끄러집니다. 두 대가 마주 보면 RMF가
중재합니다.** Mock에는 없던 것들입니다.

### 로봇 상세에서 보이는 것

```
🧊 Gazebo 시뮬레이션

주고받는 토픽
  ← /pinky_01/odom              nav_msgs/Odometry · 바퀴로 잰 위치
  ← /pinky_01/scan              sensor_msgs/LaserScan · 라이다
  ← /pinky_01/camera/image_raw  sensor_msgs/Image · 앞을 보는 카메라
  ← /pinky_01/imu_raw           sensor_msgs/Imu · 기울기와 회전
  → /pinky_01/cmd_vel           geometry_msgs/Twist · 얼마나 빨리 어디로

보고 있는 것
  ┌──────────┐  ┌────────────────────┐
  │  라이다   │  │      카메라         │
  │ (둘레 점) │  │   (앞을 본 그림)    │
  └──────────┘  └────────────────────┘
  제일 가까운 것 0.40m
```

라이다는 로봇 기준으로 그립니다 — 가운데가 로봇, 위가 앞입니다. 못 잰 점은 안
그립니다. 최대 거리로 채워 두면 없는 벽이 둘러섭니다.

### 카메라와 라이다는 어떻게 앱까지 오나

앱에는 rclpy가 없습니다. 위치는 `ros2 topic echo`로 읽지만 **카메라에는 그
방법을 쓸 수 없습니다** — 1280×720 한 장이 YAML로 2.7MB입니다.

```
Gazebo → ros_gz_bridge → <맵>_sensor_relay.py → 파일 → 앱
                          (줄여서 초당 여섯 장)
```

relay가 320×180으로 줄여 파일로 내려 주고 앱이 그 파일만 읽습니다. **실물에서도
그대로 돕니다** — 토픽 이름만 같으면 되고, Gazebo인지 진짜 카메라인지 알 필요가
없습니다.

> 화소를 파이썬 반복문으로 옮겼더니 코어 하나를 통째로 먹었습니다(101%). numpy로
> 바꾸고 초당 여섯 장으로 제한해서 22%가 됐습니다.

## 5. ③ 실제 로봇 — 맨 아래 한 겹만 바뀝니다

최초 하드웨어 기동과 안전한 수동 주행 절차는
[실제 Pinky 최초 기동과 수동 주행 절차](PHYSICAL_PINKY_FIRST_RUN.md)를 먼저
따릅니다.

### 스폰이라는 말이 없어집니다

로봇이 이미 있습니다. **Gazebo에 또 띄우면 안 됩니다** — 같은 이름이 두 번 뜹니다.
등록에서 `실제 로봇`을 고르면 Gazebo bringup이 그 로봇을 건너뜁니다.

| | fleet adapter | Gazebo bringup | 토픽 다리 |
|---|:---:|:---:|:---:|
| 앱 Mock | ✗ | ✗ | ✗ |
| Gazebo | ✓ | ✓ | ✓ |
| 실제 로봇 | ✓ | **✗** | **✗** |

들어가지 않는 로봇도 어떤 것이 있는지 생성되는 파일에 주석으로 남깁니다. 목록에서
통째로 빠지면 왜 없는지 알 수 없습니다.

### 바꿔야 할 것 셋

1. **로봇을 띄웁니다** — Gazebo 대신 `pinky_bringup`으로 진짜 모터·라이다
2. **진짜 건물을 SLAM으로 뜹니다** — 도면 지도가 실제와 다르면
3. **지도 원점을 맞춥니다** — 여기가 유일하게 손이 갑니다

SLAM 지도의 원점은 로봇이 SLAM을 시작한 자리이고, RMF의 원점은 도면 그림의 왼쪽
위입니다. 겹쳐 보고 `origin:` 세 숫자를 고칩니다. 자세한 것은
[Nav2 길](NAV2_PATH.md) §6.

### 바뀌지 않는 것

- 어댑터 코드
- Nav2 파라미터 (프레임 이름·토픽 이름)
- RMF 설정·nav graph
- 앱 화면·로봇 상세
- 센서 relay

**이것이 slotcar를 안 쓴 이유입니다.** slotcar는 지금 제일 편하지만 실물로 갈 때
통째로 버립니다.

## 6. 지금 어디까지 확인했나

정직하게 적습니다.

| | 스폰 | 센서 | 자리 잡기 | 플릿 등록 | RMF 배차 → 수행 |
|---|:---:|:---:|:---:|:---:|:---:|
| **앱 Mock** | ✅ | — | — | — | ✅ 앱이 굴림 |
| **Gazebo** | ✅ | ✅ | ✅ | ✅ | ✅ |
| **실제 로봇** | — | — | — | — | — |

Gazebo 는 끝까지 확인했습니다. `dispatch_patrol -p 픽업1` 을 넣으면 로봇이
충전1 에서 떠나 길을 따라가고, 끝나면 스스로 충전1 로 돌아옵니다.

```
[PK-01] -> (0.318, -0.902, 0도) 지도 [L1]
[pinky_01.controller_server]: Reached the goal!
[PK-01] 도착했습니다.
[PK-01] -> (1.761, -1.025, 90도) 지도 [L1]      ← 끝나면 제자리로
[PK-01] 도착했습니다.
task_id: ''                                      ← 작업 끝
```

`/pinky_01/cmd_vel` 의 발행자가 **0개에서 6개**가 됐습니다.

### 충전 Waypoint — 풀렸습니다

전에는 여기서 죽었습니다.

```
[FleetUpdateHandle::add_robot] Unable to find nearest charging waypoint.
```

`building.yaml`에 **충전1**은 있었지만 **Lane이 하나도 안 붙어 있어** nav graph로
넘어가지 못했습니다. 맵에서 홈1↔충전1 Lane을 이으니 nav graph에 waypoint가
8개에서 9개로 늘고, 그 하나가 `is_charger: true`입니다.

```
8  1.761 -1.025  {'is_charger': True, 'name': '충전1'}
홈1 -> 충전1 / 충전1 -> 홈1
```

어댑터가 통과합니다 — `gwanghee_pinky 를 Nav2 에 이었습니다. 로봇 1대`.

> **함께 나온 것** — `nav_graphs/0.yaml`은 `building.yaml`에서 파생되는데,
> 맵을 고쳐도 이 파일은 그대로 남아 있었습니다. 파일이 **없는** 것이 아니라
> **낡은** 것이라 아무 오류도 나지 않고, RMF만 옛날 지도를 봅니다. Lane을
> 이어 놓고도 같은 오류가 계속 나오던 이유입니다. 이제 실행 스크립트가
> `building.yaml`이 더 새로우면 nav graph를 다시 만듭니다.

### 어댑터가 둘이었다 — 풀렸습니다

`<맵>.launch.xml`이 띄우던 것은 `rmf_demos_fleet_adapter`였습니다. 그것은
Gazebo 안의 **slotcar 플러그인에게 직접 명령**하는 것이라 토픽으로 도는 핑키
에게는 상대가 없고, 설정에 `user`/`password`가 없어 뜨자마자 죽었습니다.

핑키를 실제로 모는 `<맵>_nav2_adapter.py`는 `<맵>_nav2.launch.xml`에 있는데
**실행 스크립트가 그것을 띄우지 않았습니다.** 그래서 `/pinky_01/cmd_vel`에
발행하는 것이 하나도 없었고, 배차는 되는데 로봇은 가만히 있었습니다.

```
Publisher count: 0        ← 명령하는 것이 없다
```

이제 이동 로봇이 토픽으로 도는 프로젝트에서는

* `<맵>.launch.xml` 이 slotcar 어댑터를 **안 붙이고**, 왜 없는지 파일 안에
  적어 둡니다.
* 실행 스크립트가 `[3/3]` 단계로 `<맵>_nav2.launch.xml` 을 띄웁니다. RMF core
  다음이라야 어댑터가 schedule node 를 찾습니다.

### 아직 거친 것 — 도착 판정

`xy_goal_tolerance` 가 벤더 기본값 **0.25m** 입니다. 그런데 이 맵은 이웃
Waypoint 사이가 **0.39m** 밖에 안 됩니다. 도착이라고 인정하는 반경이 다음
Waypoint 까지 거리의 **64%** 입니다.

실제로 충전1(1.761, −1.025) 로 돌아오라 했는데 (1.672, −0.796) 에서 멈추고
도착으로 쳤습니다 — **0.246m 어긋났습니다.** 맵 축척에 맞춰 줄여야 합니다.

그 앞 단계는 전부 확인했습니다 — 두 대를 함께 올려 서로 간섭하지 않는 것,
AMCL이 각자의 자리에서 잡는 것, 라이다·카메라가 실제로 들어오는 것.

### 실제 로봇

**하드웨어가 없어 확인하지 못했습니다.** 설계상 바뀌는 것은 맨 아래 한 겹뿐이지만,
확인하지 않은 것을 확인했다고 적지 않습니다.

## 7. 어느 것인지 화면이 늘 밝힙니다

**고른 것과 실제로 값이 오는 곳은 다를 수 있습니다.** Gazebo를 골라 놓아도 토픽이
안 오면 화면의 숫자는 여전히 앱이 계산한 값입니다. 그것을 Gazebo라고 표시하면 그
표시가 거짓말이 됩니다.

그래서 화면은 **고른 것**이 아니라 **실제로 값이 온 곳**을 표시하고, 둘이 다르면
그 사실까지 적습니다.

```
🔬 앱 Mock 데이터
   등록은 `Gazebo 시뮬레이션` 인데 앱이 아직 그 토픽을 받지 못하고 있습니다.
   아래 위치는 앱이 계산한 것입니다.
```

라이다·카메라도 같습니다. **파일이 남아 있는 것과 값이 오는 것은 다릅니다.**
relay가 죽어도 파일은 그대로라, 멈춘 그림을 실시간으로 착각하기 쉽습니다. 값이
3초 넘게 안 오면 `멈춤`으로 적고 그림을 흐리게 둡니다.
