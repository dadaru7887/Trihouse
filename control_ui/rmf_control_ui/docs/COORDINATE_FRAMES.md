# Coordinate Frames — When the Robot Is at 0,0 Instead of Home 1 (좌표계 — 로봇이 홈1이 아니라 0,0에 있을 때)

앱에는 좌표계가 **넷** 있습니다. 서로 원점도 다르고 y 방향도 다릅니다. 섞어 쓰면
로봇이 지도 원점에 그려지거나, Gazebo에서 건물 밖 허공에 놓여 **끝없이 떨어집니다.**

이 문서는 실제로 겪은 사고를 기준으로 씁니다.

---

## 1. 무슨 일이 있었나

핑키를 **홈1**에 등록해서 올렸습니다. 그런데

- 화면에서는 로봇이 지도 **0, 0** 에 있었고
- Gazebo에서는 z가 **−6,000,000 m** 까지 내려가 있었습니다.

원인이 **둘** 겹쳐 있었습니다. 하나만 고쳤으면 여전히 틀렸습니다.

| # | 원인 | 증상 |
|---|------|------|
| 1 | 앱이 **화면용 바닥 좌표**를 그대로 spawn 좌표로 썼다 | 건물 밖에 놓여 무한 낙하 |
| 2 | `/…/odom` 은 **올린 자리가 원점**이라 갓 올린 로봇은 늘 0, 0 을 낸다 | 화면에서 지도 원점에 그려짐 |

---

## 2. 좌표계 넷

### ① 지도 픽셀 — 화면이 그리는 값

그림 파일의 픽셀 그대로입니다. 원점은 **왼쪽 위**, y는 **아래로** 갈수록 커집니다.
`building.yaml` 의 `vertices:` 에 이 값이 그대로 들어갑니다.

```yaml
vertices:
  - [1537.532, 556.757, 0.0, "홈1", {is_parking_spot: [4, true]}]
```

### ② RMF 월드 좌표 (m) — Gazebo와 nav graph가 쓰는 값

RMF 지도 생성기(`rmf_building_map_tools`)가 ①을 이렇게 옮깁니다.

```
worldX =  px × 축척
worldY = −py × 축척      ← y 부호가 뒤집힌다
```

원점은 여전히 **그림의 왼쪽 위**이고, y만 **위로** 향하게 바뀝니다.
그래서 건물 안은 전부 **y가 음수**입니다.

실제 값으로 맞춰 보면:

```
축척 = 2.1100 m ÷ 1842.512 px = 0.00114518 m/px

홈1 픽셀  [1537.532, 556.757]
        → ( 1537.532 × 0.00114518,  −556.757 × 0.00114518)
        = ( 1.760744,  −0.637585)

nav_graphs/0.yaml 의 홈1: (1.760744309942079, −0.6375845964639578)   ← 정확히 일치
```

### ③ 화면용 바닥 좌표 — 사람이 읽으라고 만든 값

바닥의 **왼쪽 아래**가 원점이고 y는 **위로** 갑니다. `이름없는 3번(103, 1392)`
처럼 좌표를 보여 줄 때 씁니다. 사람이 읽기 좋으라고 만든 것이지, **실행에
쓰는 값이 아닙니다.**

②와 다른 점이 둘입니다 — **원점이 바닥 왼쪽 아래**(그림 왼쪽 위가 아님),
**y가 위로 갈수록 양수**(음수가 아님).

### ④ odom — 로봇이 켜진 자리가 원점

`/pinky_01/odom` 은 월드 좌표가 **아닙니다.** 로봇을 올린 자리에서부터 잰
값이라, 방금 올린 로봇은 언제나 **0, 0** 입니다. 실제 로봇도 같습니다 — odom은
전원을 켠 자리가 원점이고, 지도 좌표는 측위(AMCL 등)가 따로 얹어 줍니다.

---

## 3. 사고 ① — 바닥 좌표를 spawn에 넣었다

앱이 ③을 그대로 spawn 좌표로 썼습니다.

```dart
final floor = _floorCoordinate(entry.key);   // 화면용 바닥 좌표
spawnX: floor.dx * scale,
spawnY: floor.dy * scale,                    // ← y가 양수로 나간다
```

그 결과 홈1의 핑키가 이렇게 나갔습니다.

```
앱이 적은 값   (1.642,  +1.595)
RMF가 아는 홈1 (1.761,  −0.638)
```

y 부호가 반대입니다. 그리고 바닥 메시가 있는 곳은:

```
generated_models/gwanghee_L1/meshes/floor_1.obj
  x: 0.063 ~ 2.230
  y: −2.664 ~ −0.107      ← 음수 구간에만 바닥이 있다
```

**y = +1.595 에는 바닥이 없습니다.** 로봇은 허공에 놓여 떨어지기 시작했습니다.

```
[1.642000 1.595000 −6007360.000000]
[1.642000 1.595000 −6033970.000000]
[1.642000 1.595000 −6060860.000000]     ← 3초에 5만 m씩
```

x, y가 그대로인 것은 옆으로 미는 힘이 없어서입니다. 바퀴는 허공에서 돌고
있었으므로 **odom은 정상으로 보였습니다.** 그래서 토픽만 봐서는 알 수
없었습니다.

### 왜 옆의 OMX는 멀쩡했나

설치 로봇은 월드에 고정되어 있어 **떨어지지 않습니다.** 좌표는 똑같이 틀렸지만
증상이 안 보였습니다. 이동 로봇만 티가 났습니다.

### 고친 뒤 확인

떨어지던 모델을 지우고 고친 좌표로 다시 올렸습니다.

```
$ ros2 run ros_gz_sim create -world sim_world -name pinky_01 \
    -topic /pinky_01/robot_description -x 1.7607 -y -0.6376 -z 0.1

[1.760700 −0.637600 −0.000001]
[1.760700 −0.637600 −0.000001]
[1.760700 −0.637600 −0.000001]      ← 바닥에 안착, 정지
```

> **주의** — 이미 떨어지고 있는 로봇은 `set_pose` 로 자리만 옮겨도 소용없습니다.
> 속도가 남아 있어서(초속 1만 7천 m) 한 스텝에 바닥을 뚫고 다시 떨어집니다.
> 반드시 **지우고 다시 올려야** 합니다.

## 4. 사고 ② — odom을 월드 좌표로 착각했다

`/pinky_01/odom` 을 그대로 화면에 그렸습니다. 갓 올린 로봇은 0, 0 을 내므로
홈1에 세워 둔 로봇이 지도 원점에 그려졌습니다.

올린 자리를 앞에 붙여야 합니다.

```
worldX = spawnX + odomX·cos θ − odomY·sin θ
worldY = spawnY + odomX·sin θ + odomY·cos θ
worldθ = spawnθ + odomθ
```

`RobotPose.toWorld()` 가 이것입니다. 자리를 모르면 받은 값을 그대로 둡니다.

odom은 시간이 지나면 미끄러짐이 쌓입니다. 시뮬레이터에서는 충분하지만, 실물
로봇에서는 측위가 낸 지도 좌표를 받아야 합니다.

---

## 5. 정리 — 어느 값을 어디에 쓰나

| 쓰는 곳 | 좌표계 | 만드는 함수 |
|---------|--------|-------------|
| `building.yaml` 의 vertices | ① 지도 픽셀 | 그대로 |
| **spawn 좌표**, nav graph, Gazebo | ② RMF 월드 (m) | `rmfWorldFromPixel()` |
| 화면에 좌표 보여 주기 | ③ 화면용 바닥 | `_floorCoordinate()` |
| 토픽이 준 위치를 화면에 그리기 | ② → ① | `pixelFromRmfWorld()` |
| 토픽 원본 | ④ odom | `RobotPose.toWorld()` 로 ②로 옮김 |

**규칙 하나만 기억하면 됩니다 — 실행에 나가는 값은 전부 ②입니다.**
③은 사람 눈에만 보여 줍니다.

## 6. 좌표를 맞추는 과정 — `로봇 → 자리 맞추기`

좌표는 눈에 안 보이는 값이라 틀려도 티가 안 납니다. 그래서 **로봇 메뉴에
`자리 맞추기`** 를 두었습니다. 버튼 자체가 먼저 알립니다.

| 버튼 모양 | 뜻 |
|-----------|-----|
| `자리 맞추기` (평소) | 문제 없음 |
| 🟠 `자리 맞추기 · 2대` | 자리가 지도와 다르거나 자리를 못 찾음 |
| 🔴 `자리 맞추기 · 1대` | **바닥 밖** — 이대로 올리면 이동 로봇이 떨어짐 |

### 창에서 보는 것

```
축척   0.001145 m/px  (873 px/m)
바닥   x 0.06 ~ 2.23 m · y −2.66 ~ −0.11 m
결과   1대가 바닥 밖에 있습니다

┌───────────────────────────────────────────────────┐
│ ⚠ PK-01 · 핑키 1호                      [바닥 밖] │
│   자리   홈1 (충전)                                │
│   저장   1.642, 1.595 m                           │
│   지도   1.761, −0.638 m  ← 맞추면 이 값이 됩니다  │
│   저장된 자리에 바닥이 없습니다. 이대로 올리면      │
│   이동 로봇은 허공에서 끝없이 떨어집니다.          │
│   방향   [0° 오른쪽 ▾]  이 자리에서 볼 방향입니다  │
└───────────────────────────────────────────────────┘

           [복사]  [지도 기준으로 맞추기 · 1대]  [닫기]
```

**판정은 지도에서 다시 계산한 값이 아니라 지금 저장된 값을 봅니다.** 실행에
실제로 나가는 것이 저장된 값이기 때문입니다.

### 판정 다섯

| 판정 | 뜻 | 맞추기로 풀리나 |
|------|-----|----------------|
| 맞습니다 | 지도와 같고 바닥 안 | — |
| **바닥 밖** | 그 자리에 바닥이 없다 | ✅ |
| 지도와 다름 | 자리 Waypoint 를 옮겼거나 예전 값 | ✅ |
| 좌표 없음 | 아직 자리를 안 정했다 | ✅ |
| 자리 없음 | 적힌 Waypoint 를 지도에서 못 찾음 | ❌ 로봇 등록에서 자리를 다시 고른다 |

### 방향

`방향` 은 그 자리에서 로봇이 볼 쪽입니다. 스폰 launch 의 `-Y` 로 나갑니다.
8방위 중에 고릅니다 — 자리에 세우는 것이지 정밀 정렬이 아닙니다.

### 순서

1. **맵 관리** 에서 길이 기준(축척)을 잽니다 — 이것이 없으면 아무것도 판정할 수 없습니다
2. **맵 관리** 에서 바닥을 그리고 자리 Waypoint(충전·설비)를 찍습니다
3. **로봇** 에서 로봇을 등록하고 자리를 고릅니다
4. **로봇 → 자리 맞추기** 로 확인하고, 어긋난 것이 있으면 맞춥니다
5. 백엔드를 **내렸다가 다시 띄웁니다** — 이미 올라간 로봇은 안 바뀝니다

---

## 7. 예전에 저장해 둔 프로젝트는

앱이 프로젝트를 열 때와 백엔드를 띄우거나 내릴 때 **자리를 지금 지도 기준으로
다시 계산합니다**(`robotsWithMapSpawnPoints`). spawn 좌표는 언제나 자리
Waypoint에서 나오므로 다시 계산해도 잃을 것이 없습니다. 이름·모델·구획 자격은
건드리지 않습니다.

자리 Waypoint를 못 찾은 로봇은 **건드리지 않습니다.** 지도가 아직 안 올라온
사이에 불릴 수 있고, 그때 지워 버리면 멀쩡한 등록이 좌표를 잃습니다.

**다만 이미 Gazebo에 올라가 있는 로봇은 그대로입니다.** 고친 자리로 올리려면
백엔드를 내렸다가 다시 띄워야 합니다.

## 8. 다시 겪지 않으려면

무한 낙하는 **토픽만 봐서는 안 보입니다.** 바퀴가 허공에서 돌아도 odom은
정상으로 나옵니다. 의심되면 월드에서 직접 확인하세요.

```bash
gz model -m pinky_01 -p
```

z가 0 근처가 아니면 바닥 밖입니다. 바닥이 어디 있는지는 이렇게 봅니다.

```bash
grep "^v " <맵>/generated_models/<맵>_L1/meshes/floor_1.obj \
  | awk '{if(NR==1){miny=maxy=$3} if($3<miny)miny=$3; if($3>maxy)maxy=$3}
         END{print "y:", miny, "~", maxy}'
```

건물 안이면 **y가 음수**여야 합니다. 등록한 로봇의 spawn 좌표에 양수 y가 보이면
그것이 바로 이 사고입니다.

## `map` 과 `odom` 이 벌어질 때

`odom` 은 로봇을 올린 자리를 원점 삼아 바퀴 회전을 더해 가는 값이라 미끄러지면
그만큼 어긋납니다. AMCL 이 `map→odom` 으로 그 차이를 되돌립니다.

평소에는 작지만 크게 벌어질 때가 있습니다. 실제로 이렇게 됐습니다.

```
map → pinky_02/odom :  이동 (0.938, -0.229),  회전 -46.07°
```

로봇이 복구 동작(제자리 회전·후진)을 되풀이하면서 바퀴만 돌고 몸은 안 움직여,
`odom` 에 헛회전이 쌓인 것입니다. 그 복구가 왜 돌았는지는
[SIMULATION_TIME.md](SIMULATION_TIME.md) §1.3 에 있습니다.

그래서 화면에 로봇을 그릴 때는 **`map` 좌표를 써야 합니다.** 앱은 RMF 가 내는
`/fleet_states` 를 읽습니다 — RViz 가 그리는 것과 같은 값입니다.
