## 1. 개요

`robo_control`은 3온도 물류센터의 **관제 계층(FMS)** 이다. 지금까지 로봇 거동은
관제센터 프로세스 안에서 수식으로 계산됐다. 관제 로직을 검증하기에는 충분하지만,
"로봇이 실제로 그 자리에 갈 수 있는가"는 확인할 수 없었다.

`robo_pinky`는 그 자리에 **Gazebo 물리 엔진 위에서 움직이는 Pinky 로봇**을 넣는다.
관제는 더 이상 이 로봇들의 위치를 계산하지 않는다.

| | 시뮬레이션 로봇 `RS-xx` | 현장 로봇 `PK-xx` |
|---|---|---|
| 위치·방위 | 관제가 적분 | **로봇이 물리 엔진 위에서 움직인 결과를 보고** |
| 배터리 | 관제가 계산 | **로봇이 주행량·구획 온도로 계산해 보고** |
| 관제가 내리는 것 | (없음) | 경로 웨이포인트 · 안전 정지 · 속도 상한 · 충전 |
| 배차·FEFO·안전·재고 | 동일 | 동일 |

즉 이 프로젝트는 **관제 로직을 바꾸지 않은 채 로봇 거동만 실물로 교체**해,
실장비 투입 전에 통제 계층을 검증하는 하네스다.

### 이름의 대상

Pinky는 PinkLab의 교육용 차동구동 로봇이다. 이 저장소의 URDF는 공개
`pinky_description`(pinky_for_edu)의 치수를 따르되, 메시 대신 기본 도형으로
재구성해 자체 완결성과 다중 스폰 성능을 확보했다(§6).

## 2. 설계 목표

| ID | 목표 | 판정 기준 |
|---|---|---|
| **G-01** | 관제 로직을 수정하지 않고 실물 로봇을 붙인다 | 배차·FEFO·안전·재고 코드 경로가 두 로봇 종류에서 동일 |
| **G-02** | 관제 평면도와 물리 월드가 일치한다 | 관제가 계획한 통로 경로를 로봇이 물리적으로 통과할 수 있다 |
| **G-03** | 로봇이 관제보다 우선하는 자기 안전 장치를 갖는다 | 관제가 모르는 장애물 앞에서 스스로 정지하고 사유를 보고 |
| **G-04** | 링크 단절이 데이터 정합성을 깨지 않는다 | 끊긴 로봇의 태스크·리스·자원이 자동 회수되어 재할당 |
| **G-05** | 여러 대를 한 월드에 띄운다 | 링크·프레임·토픽이 로봇별로 분리 |
| **G-06** | 관제 없이는 움직이지 않는다 | 링크 미연결 시 로봇은 정지 상태 유지 |

## 4. 좌표계

관제센터 `WarehouseLayout`는 **화면 좌표계**다. 폭 120 × 높이 72 unit, 원점은
좌상단, y가 **아래로** 증가한다. Gazebo 월드는 창고 중심이 원점인 미터 단위
우수 좌표계다.

```
관제 → 월드                      월드 → 관제
x_m = (x_u - 60) * 0.1          x_u = x_m / 0.1 + 60
y_m = (36 - y_u) * 0.1          y_u = 36 - y_m / 0.1
yaw = -heading_u                heading_u = -yaw
```

y축이 뒤집히므로 **회전 방향도 부호가 반대**다. 이 변환은 두 곳에 같은 식으로
구현되어 있으며, 한쪽을 고치면 다른 쪽도 함께 고쳐야 한다.

- Python: [`robo_pinky_agent/frames.py`](../src/robo_pinky_agent/robo_pinky_agent/frames.py) `WarehouseFrame`
- 월드 생성: [`generate_world.py`](../src/robo_pinky_sim/scripts/generate_world.py) `mx()` / `my()`
- 런치 스폰: [`warehouse.launch.py`](../src/robo_pinky_sim/launch/warehouse.launch.py) `_to_world()`

### 축척을 0.1 m/unit로 잡은 이유

관제 문서의 명목 축척은 1 unit ≈ 0.5 m(창고 60 m × 36 m)다. 그대로 쓰면
Pinky(최고 0.5 m/s)가 창고를 가로지르는 데 2분이 넘어 관찰이 어렵다.

**0.1 m/unit**로 축소하면

| 항목 | 값 |
|---|---|
| 창고 | 12 m × 7.2 m |
| 통로 간격 | 세로 1.5 m · 가로 1.6 m |
| 랙 폭(깊이) | 0.52 m |
| 관제 기본 주행 속도 3.4 unit/s | **0.34 m/s** — Pinky 정격(0.5 m/s) 안 |
| 안전 보호 필드 3.5 unit | 0.35 m |

축척은 런치 인자 `scale`과 `welcome` 메시지로 양쪽에 전달되므로, 값을 바꾸면
월드를 재생성하고 런치 인자만 맞추면 된다.

## 5. 월드 모델

`warehouse_3temp.sdf`는 손으로 쓰지 않고 **레이아웃 상수에서 생성**한다.

```bash
python3 src/robo_pinky_sim/scripts/generate_world.py \
        src/robo_pinky_sim/worlds/warehouse_3temp.sdf
```

생성 스크립트 상단의 상수는 `robo_control/lib/core/layout.dart`와 1:1로 대응한다
(`CORRIDOR_X` `CORRIDOR_Y` `RACK_ROW_Y` `ZONE_BOUNDS` `STATIONS`). 평면도를 바꾸면
양쪽 상수를 맞춘 뒤 다시 돌린다.

### 구성물

| 요소 | 내용 |
|---|---|
| 바닥 | 구획별 색 구분 — 상온 −6.0~−1.0 m · 냉장 −1.0~2.8 m · 냉동 2.8~6.0 m |
| 외벽 | 높이 0.30 m, 두께 0.06 m |
| 랙 | 4열 × 8구간 = **32개**. 높이 0.32 m, 깊이 0.52 m |
| 스테이션 | 17개(입고 2 · 출고 2 · 충전소 4 · 작업대 3 · **적재 3** · 대기 2 · 집결지 1). 바닥 데칼 + 충전소 기둥 |
| 조명 | 구획별 점광원. 밝기 1.0 / 0.75 / 0.55 — 조도 320 / 240 / 180 lx에 대응 |
| 물리 | `max_step_size` 0.002 s, `real_time_factor` 1.0 |

### 랙을 8구간으로 나눈 이유 (G-02)

관제의 통로 그래프는 세로 통로(x = 5, 20, 35, 50, 65, 80, 95, 110)와 가로 통로가
교차하는 격자다. 관제 화면에서 랙은 폭 전체를 가로지르는 막대로 그려지지만,
로봇은 그 위를 지나는 세로 통로를 따라 이동한다.

물리 월드에서 랙을 통짜 막대로 만들면 **관제가 계획한 경로를 로봇이 통과할 수
없다.** 그래서 세로 통로가 지나는 자리마다 ±2.8 unit(0.28 m × 2 = 0.56 m)을
비워 8구간으로 쪼갠다.

```
행당 랙 구간 (unit)
[8.0, 17.2] [22.8, 32.2] [37.8, 47.2] [52.8, 62.2]
[67.8, 77.2] [82.8, 92.2] [97.8, 107.2] [112.8, 116.0]
        ↑ 20        ↑ 35        ↑ 50   … 세로 통로가 지나는 자리
```

## 6. 로봇 모델

### 치수

| 항목 | 값 | 출처 |
|---|---|---|
| 섀시 | 100 × 80 × 60 mm | `pinky_description` |
| 바퀴 | ø60 mm, 두께 14 mm | `pinky_description` |
| 축간 거리(조인트) | 110 mm | `pinky_description` |
| 캐스터 | ø20 mm, 섀시 뒤 44 mm | `pinky_description` |
| 질량 | 섀시 1.0 kg · 바퀴 0.05 kg · 캐스터 0.10 kg | `pinky_description` |

> **알아 둘 점** — DiffDrive 플러그인의 `wheel_separation`은 조인트 간격(0.11 m)이
> 아니라 **0.096 m**다. 참조 description이 오도메트리 보정을 위해 쓰던 값을 그대로
> 가져왔다. 실기 오도메트리와 맞추려는 튜닝 값이므로 조인트 위치와 다르다는 점을
> 알고 다뤄야 한다.

### 메시 대신 기본 도형을 쓴 이유

원본 `pinky_description`의 시각 메시는 약 7 MB(base_link 2.5 MB, lidar 2.1 MB,
wheel 0.9 MB …)다. 3대를 스폰하면 로딩과 렌더 비용이 그만큼 늘고, 저장소에
서드파티 바이너리를 복사해 넣어야 한다.

이 저장소는 **동일 치수의 기본 도형**(박스·실린더·구)으로 재구성했다. 자체
완결적이고, 다중 스폰이 가볍고, 본체 색으로 로봇을 구분할 수 있다. 시각 메시가
필요하면 `pinky_description`을 워크스페이스에 함께 두고 visual 지오메트리만
교체하면 된다.

### 센서

| 센서 | 사양 | 기본 |
|---|---|---|
| 2D 라이다 (LD06 상당) | 360 샘플, 360°, 10 Hz, 0.10~6.0 m, σ 0.01 m | 켬 |
| IMU | 100 Hz | 켬 |
| 전방 카메라 | 640×360, 15 Hz, FOV 1.08 rad | **끔** (`camera:=true`) |

카메라를 기본 비활성으로 둔 이유는 §11.4.

### 다중 스폰 분리

`robot_name`(예: `pinky_01`)으로 링크 이름과 gz 토픽을 모두 분리한다.

| | 형식 | 예 |
|---|---|---|
| 링크·프레임 | `<robot_name>/<link>` | `pinky_01/base_footprint` |
| gz 토픽 | `/<robot_name>/<topic>` | `/pinky_01/cmd_vel` |

프레임 이름에 접두어가 박혀 있으므로 `robot_state_publisher`에 `frame_prefix`를
따로 줄 필요가 없고, 여러 대가 `/tf` 하나를 공유해도 충돌하지 않는다.

### ROS 토픽 (로봇당)

| 토픽 | 타입 | 방향 |
|---|---|---|
| `/pinky_0N/cmd_vel` | `geometry_msgs/Twist` | ROS → GZ |
| `/pinky_0N/odom` | `nav_msgs/Odometry` | GZ → ROS |
| `/pinky_0N/scan` | `sensor_msgs/LaserScan` | GZ → ROS |
| `/pinky_0N/imu` | `sensor_msgs/Imu` | GZ → ROS |
| `/pinky_0N/joint_states` | `sensor_msgs/JointState` | GZ → ROS |
| `/pinky_0N/tf` → `/tf` | `tf2_msgs/TFMessage` | GZ → ROS |
| `/pinky_0N/link_status` | `std_msgs/String` | 에이전트 발행(사람이 읽는 한 줄 요약) |
| `/clock` | `rosgraph_msgs/Clock` | GZ → ROS (전역 1개) |

### 오도메트리 합성

Gazebo DiffDrive의 `odom`은 **스폰 지점을 원점**으로 한다. 월드 포즈는 스폰 포즈를
앞에 합성해 얻는다.

```
월드 포즈 = 스폰 포즈(월드) ⊕ odom(스폰 기준)
```

`frames.compose()`가 이 계산을 담당한다. 별도의 지상 진리 포즈 토픽을 브리지하지
않아도 되고, 스폰 포즈는 런치와 에이전트 파라미터에 같은 값이 들어간다.

## 7. 적재 스테이션과 로봇팔

구획마다 **OpenMANIPULATOR-X 적재 로봇팔**이 한 대씩 있다. 출고 태스크는 랙에서
집품한 뒤 이 자리를 거쳐 도크로 간다.

```
출고 태스크 (적재 스텝 도입 후)

  1. C-01-09 랙으로 이동
  2. 집품 — 요구르트 12입 3개
  3. LOAD-C 적재 스테이션으로 이동      ← 추가
  4. LOAD-C 로봇팔이 요구르트 3개 적재  ← 추가
  5. OUT-1 출고 도크로 이동
  6. 하역 및 검수
```

관제 → 팔 : `{"t":"load","robot":"PK-01","task":"TSK-0042","item":"…","x":68.3,"y":38.0}`
팔 → 관제 : `{"t":"loaded","id":"OMX-C","task":"TSK-0042"}`

### 배치 제약 — 팔은 아무 데나 세울 수 없다

받침대는 **관제가 모르는 실물 장애물**이다. 관제의 경로 계획은 통로 그래프와
랙 진입선만 알기 때문에, 그 위에 장애물이 있으면 로봇이 그대로 처박힌다.

처음에는 구획 작업 스테이션(WS-1/2/3) 옆에 팔을 세웠다. 그 결과

- WS는 **세로 통로와 가로 통로의 교차점**이라 통과 교통이 지나가고,
- 팔이 통로(y=38)와 랙 열(y=30) 사이에 놓여 **그 랙으로 집품하러 가는 로봇의
  진입선을 막았다.**

로봇은 팔 앞 0.10 m에서 라이다 정지한 뒤 빠져나오지 못했다.

그래서 **전용 적재 스테이션 `LOAD-A` · `LOAD-C` · `LOAD-F`** 를 새로 두었다.
좌표는 세 조건을 모두 만족해야 한다.

| 조건 | 이유 |
|---|---|
| 세로 통로 x(5·20·35…)에서 3 unit 이상 | 통과 교통을 막지 않는다 |
| 랙 로케이션 x(9.5 + 5.6·c)에서 2.5 unit 이상 | 랙 진입선을 막지 않는다 |
| 스테이션에서 2.8 unit(0.28 m) 이내 | 팔 사거리 안에 로봇이 들어온다 |

이웃한 랙 열 두 개의 정중앙이 답이다.

| 스테이션 | 구획 | 로봇 정차 위치 | 팔 받침대 |
|---|---|---|---|
| `LOAD-A` | 상온 | (40.3, 38) | (40.3, 35.2) |
| `LOAD-C` | 냉장 | (68.3, 38) | (68.3, 35.2) |
| `LOAD-F` | 냉동 | (101.9, 38) | (101.9, 35.2) |

받침대 단면도 0.12 → **0.06 m**로 줄여 통로 여유를 확보했다.

> 이 좌표는 `robo_control/lib/core/layout.dart`와 `config/arms.yaml`,
> `generate_world.py` 세 곳에 같은 값이 있어야 한다.

### 팔 모델

관절 원점·축·가동범위는 ROBOTIS `open_manipulator_description`의
open_manipulator_x와 동일하다.

| 관절 | 축 | 원점(부모 기준) | 가동범위 |
|---|---|---|---|
| joint1 | z | (0.012, 0, 0) | ±π |
| joint2 | y | (0, 0, 0.0595) | ±1.5 |
| joint3 | y | (0.024, 0, 0.128) | −1.5 ~ 1.4 |
| joint4 | y | (0.124, 0, 0) | −1.7 ~ 1.97 |
| gripper ×2 | y(직동) | (0.0817, ±0.021, 0) | −0.011 ~ 0.02 m |

끝단은 joint4에서 0.126 m. 받침대 높이 0.18 m 위에 세워 로봇 적재 데크
(z ≈ 0.076 m)를 내려다본다. 유효 사거리는 0.15 ~ 0.28 m로 제한한다
(0.32 m는 데크 높이에서 도달 불가).

### 역기구학

joint2/3/4가 모두 y축이므로 어깨부터 끝단까지는 **평면 3링크**다. 여유
자유도 하나는 끝단 접근 각도(`pitch`)로 고정해 해를 유일하게 만든다.

```
A = j2 + α,  B = j2 + j3 + π/2,  C = j2 + j3 + j4 + π/2      (각각 +z에서 기운 각)
C = π/2 − pitch                                              (접근 각도로 고정)
손목중심 W = 끝단 − 0.126·(sin C, cos C)   → 2링크로 풀고 되돌린다
α = atan2(0.024, 0.128) = 0.1855           (상완의 고유 꺾임)
```

팔꿈치 위·아래 두 해 중 가동범위를 만족하는 쪽을 쓴다. 구현은
[`arm_kinematics.py`](../src/robo_pinky_agent/robo_pinky_agent/arm_kinematics.py).

**검증** — 도달 가능한 471개 표본에서 정기구학으로 되돌린 위치 오차 1.3e-16 m,
자세 오차 3.3e-16 rad(기계 정밀도).

### 적재 궤적

팔은 관제가 보내 준 **로봇의 실제 위치**로 역기구학을 풀어 내려놓는다. 로봇이
사거리 밖에 서 있으면 방향은 유지한 채 거리만 잘라 접근한다.

| 구간 | 동작 | 시간 |
|---|---|---|
| 1 | 화물대 위 접근 (그리퍼 열림) | 1.2 s |
| 2 | 화물 높이로 하강 | 1.0 s |
| 3 | **그리퍼 닫음** | 0.8 s |
| 4 | 들어올림 | 1.0 s |
| 5 | **로봇 위로 선회** (joint1 π → 0) | 1.6 s |
| 6 | 데크로 하강 | 1.0 s |
| 7 | **그리퍼 열림 — 적재** | 0.8 s |
| 8 | 상승 | 0.9 s |
| 9 | 홈 자세 복귀 | 1.3 s |

총 9.6 s. 에이전트가 20 Hz로 코사인 이징 보간해 관절 목표를 publish한다.

> **화물의 물리적 파지는 모사하지 않는다.** 그리퍼 개폐와 궤적은 실제로
> 움직이지만 화물 객체가 손에 붙지는 않는다. 화물 인수인계는 관제 원장이
> 관리한다(`Robot.payload`).

### 관절 구동 — 왜 힘 PID가 아니라 속도 지령인가

처음에는 `gz-sim-joint-trajectory-controller-system`(힘 기반 PID)을 썼다.
링크가 0.08~0.14 kg으로 가벼운데도 **관절마다 0.15~0.27 rad의 정상 상태 오차**가
남았고, 게인을 6배로 올려도 수렴하지 않았다(오히려 악화).

관절마다 `gz-sim-joint-position-controller-system`을 두고
`<use_velocity_commands>true</use_velocity_commands>`로 바꾸자 오차가
**0.0000 rad**이 되었다. 컨트롤러가 힘이 아니라 관절 속도를 직접 지령하므로
중력에 밀리지 않는다.

대신 부드러운 가감속은 시뮬레이터가 아니라 **에이전트가 만든다** — 웨이포인트
사이를 20 Hz로 코사인 이징 보간한다.

## 8. 링크 프로토콜

**proto 1** · TCP · 한 줄 = JSON 한 건(NDJSON, UTF-8) · 기본 `127.0.0.1:8788`

관제센터가 **서버**, 로봇 온보드 에이전트가 **클라이언트**다. 로봇이 붙었다 떨어지는
쪽이므로 이 방향이 자연스럽고, 관제는 접속 목록만 관리하면 된다.

### 로봇 → 관제

#### `hello` — 최초 1회

```json
{"t":"hello","proto":1,"id":"PK-01","name":"핑키 1호","model":"PINKY-GZ-C",
 "zones":["ambient","chilled","frozen"],"charger":"CHG-1",
 "x":50.0,"y":22.0,"heading":0.0,"battery":92.0}
```

| 필드 | 의미 |
|---|---|
| `id` | 관제 플릿 ID. **없는 ID면 신규 등록**, 있으면 복귀 처리 |
| `model` | `PINKY`으로 시작하면 관제가 **링크 전용 기종**으로 취급(§9) |
| `zones` | 진입 가능 구획. `ambient`/`chilled`/`frozen` 또는 `A`/`C`/`F` |
| `charger` | 홈 충전소 ID. 없거나 잘못되면 대응 구획에서 자동 배정 |
| `x` `y` `heading` `battery` | 접속 시점 상태 |

#### `telemetry` — 주기 보고 (5 Hz)

```json
{"t":"telemetry","id":"PK-01","x":62.5,"y":42.0,"heading":-1.57,
 "battery":93.1,"speed":3.2,"odom":118.4,"wpLeft":3,
 "charging":false,"note":null,"seq":7}
```

`x` `y` `speed` `odom`은 **관제 unit** 단위다(로봇이 변환해 보낸다).
`note`는 로봇이 스스로 멈춘 사유이며, 관제 상세 패널의 **안전 메모**에 표시된다.

#### `log` — 관제 이력 적재

```json
{"t":"log","id":"PK-01","sev":"warning","msg":"전방 장애물로 12초째 정지 …"}
```

`sev`는 `info` / `warning` / `serious` / `critical`.

### 관제 → 로봇

| 종류 | 페이로드 | 의미 |
|---|---|---|
| `welcome` | `{"scale":0.1,"width":120.0,"height":72.0}` | 좌표계 파라미터. 이걸 받아야 등록 완료 |
| `path` | `{"seq":12,"goalTol":5.0,"label":"C-02-07","waypoints":[[x,y],…]}` | 주행 경로(unit). **빈 배열이면 정지** |
| `hold` | `{"on":true,"reason":"작업자 위급 반경 내 정지"}` | 안전 정지 래치 |
| `speed` | `{"limit":2.4}` | 허용 속도 상한(unit/s) |
| `charge` | `{"on":true}` | 충전 개시/종료 |

`speed`의 `limit`에는 관제가 계산한 모든 감속 요인이 이미 반영되어 있다 —
구획 환경 지수, 작업자 안전 필드(보호 필드에서는 0), 선행 로봇 양보, 절전 모드,
적재 여부.

### 적재 로봇팔 메시지

팔은 `hello`에 `"kind":"arm"`을 실어 **적재 장비**로 등록한다. 관제는
`station` ID로 팔을 찾는다.

**팔 → 관제**

| 종류 | 내용 |
|---|---|
| `hello` | `{"kind":"arm","id":"OMX-C","station":"LOAD-C","zone":"chilled","model":"OMX-LOADER"}` |
| `armStatus` | 주기 보고. `status`(idle/loading) · `done`(누적 적재 건수) |
| `loaded` | `{"id":"OMX-C","task":"TSK-0042"}` — 적재 완료 |
| `loadFailed` | `+ "reason"` — 사거리 초과·중복 지시 등 |

**관제 → 팔**

| 종류 | 내용 |
|---|---|
| `welcome` | 좌표계 파라미터 |
| `load` | `{"robot":"PK-01","task":"…","item":"…","qty":3,"x":68.3,"y":38.0}` — `x`/`y`는 **로봇이 실제로 선 자리**(관제 unit) |
| `abort` | 진행 중 적재 취소(로봇 이탈·타임아웃) |

### 전송 정책

| 상황 | 동작 |
|---|---|
| 경로가 이전에 보낸 것의 **남은 구간**이면 | 재전송하지 않음 (로봇과 관제가 같은 규칙으로 웨이포인트를 줄이므로) |
| `hold`/`speed`/`charge` 값이 그대로면 | 재전송하지 않음 (`speed`는 0.05 unit/s 이내 변화 무시) |
| 미연결 상태에서 텔레메트리 | 조용히 폐기 (최신값이 곧 진실) |
| 소켓 오류 | 해당 링크를 `dead` 표시하고 더 쓰지 않음 |

### 연결 수명

```
로봇                              관제
 │ connect ───────────────────────▶│
 │ hello ─────────────────────────▶│  플릿 등록 / 복귀
 │◀───────────────────────── welcome│
 │ telemetry (5 Hz) ──────────────▶│  위치·배터리 반영
 │◀──────────── path/hold/speed/… │  tick(5 Hz)마다 필요 시
 │                                 │
 │ ✕ 단절                          │  태스크 회수 · 리스/자원 해제
 │                                 │  → 예비 대기, 배차 제외
 │ 재접속(백오프 0.5→5 s) ────────▶│
 │ hello ─────────────────────────▶│  복귀
```

로봇 측은 링크가 끊기면 **즉시 정지**하고 마지막 명령을 유지하지 않는다(G-06).

## 9. 온보드 제어 루프

`pinky_agent`는 두 개의 타이머로 돈다.

| 타이머 | 주기 | 하는 일 |
|---|---|---|
| 제어 | 20 Hz | 정지 조건 판정 → 경로 추종 → `cmd_vel` 발행 → 배터리 적분 |
| 보고 | 5 Hz | `telemetry` 송신 + `link_status` 발행 |

### 정지 조건 우선순위

```
1. 링크 미연결        → 정지  "관제 링크 단절 — 안전 정지"
2. hold 래치          → 정지  (관제가 준 사유 그대로)
3. 충전 중            → 정지  "충전 중"
4. 전방 장애물        → 전진만 정지 (회전은 허용)
5. 그 외              → 경로 추종
```

4번이 **전진만** 막는 것이 중요하다(§11.2).

### 경로 추종

Pinky는 제자리 회전이 가능한 차동구동이고 통로가 좁다. 곡률 추종보다
**회전 정렬 → 직진**이 안정적이다.

| 파라미터 | 값 | 의미 |
|---|---|---|
| `reach` | 0.12 m (1.2 unit) | 경유 웨이포인트 소진 반경 |
| `goal_reach` | 0.50 m (5.0 unit) | **종점** 도착 반경. `goalTol`로 관제가 지정 |
| `align_tol` | 0.45 rad | 이보다 크면 제자리 회전만 |
| `max_linear` | 0.34 m/s | 상한. `speed` 명령과 min |
| `max_angular` | 1.6 rad/s | |
| `k_angular` | 2.4 | 방위 오차 비례 이득 |
| `slow_radius` | 0.25 m | 종점 감속 시작 거리 |

방위 오차가 클수록 선속도를 최대 65 %까지 낮춰 곡선 구간에서 이탈을 줄인다.

### 전방 감시

라이다 전방 ±35°(`obstacle_fov_deg` 70°) 최소 거리가 `obstacle_stop_distance`
0.15 m보다 가까우면 전진을 막는다. 라이다는 섀시 중심 위에 있으므로,
랙 앞에서 정지하면 로봇 중심은 선반 표면에서 0.15 m, 선반 중심선에서
0.15 + 0.26 = **0.41 m(4.1 unit)** 떨어진다 — 종점 반경 5.0 unit 안이다.

10초 이상 장애물로 멈춰 있으면 `log`를 한 번 올려 관제 이력에 남긴다.

### 배터리 모델

관제센터 `FleetEngine`과 같은 축척을 쓴다.

```
방전율 = (0.012 + 0.085 × 속도비) × 저온계수     [%/s]
충전율 = 0.55                                    [%/s]
저온계수 = 상온 1.0 · 냉장 1.12 · 냉동 1.35
```

로봇이 계산해 보고하므로, 관제는 링크된 로봇에 대해 자체 방전 계산을 건너뛴다.
배터리 **정책**(20 % 절전, 10 % 충전소 복귀, 95 % 복귀)은 여전히 관제가 판단한다.

## 10. 관제센터 측 변경

`robo_control`에 추가된 것은 링크 서버 한 개와 `FleetEngine`의 훅 몇 군데다.
배차·FEFO·안전·재고 로직은 손대지 않았다(G-01).

### 새 파일

[`lib/core/robot_link.dart`](../../robo_control/lib/core/robot_link.dart) —
`RobotLinkServer`(TCP 서버 · 프로토콜), `LinkedRobot`(접속 1건), `RobotHello`,
`RobotTelemetry`.

### `FleetEngine` 훅

| 위치 | 동작 |
|---|---|
| `tick()` 선두 `_pullTelemetry()` | 보고된 위치·방위·배터리·속도·주행거리를 로봇 상태에 반영 |
| `tick()` 말미 `_pushLinkCommands()` | `hold` · `charge` · `speed` · `path` 하달 |
| `_advance()` | 링크된 로봇이면 적분하지 않고 `_advanceLinked()` — 실제로 지난 웨이포인트만 소진 |
| `_drain()` | 링크된 로봇이면 건너뜀 (로봇이 보고) |
| `charging` 분기 | 링크된 로봇이면 배터리를 더하지 않음 (로봇이 보고) |
| `_stepRobot()` 선두 | **링크 전용 기종인데 미접속**이면 예비 대기로 내리고 배차 제외 |
| `_fleetScaling()` / `_requestBackfill()` | 미접속 링크 기종을 예비 투입 후보에서 제외 |
| `_buildOutboundTask()` | 집품 뒤에 **적재 스테이션 이동 + 적재** 스텝 2개 삽입 |
| `_runTask()` 적재 스텝 | `_serveLoadStep()` — 팔에 지시하고 완료 보고를 기다린다 |
| `_advanceLinked()` | `_watchStall()` — 진행 정체 감시 |

### 적재 스텝 처리 (`_serveLoadStep`)

이 구획 적재 스테이션에 **실물 팔이 접속해 있고 로봇도 실장비일 때만** 팔에
지시한다. 둘 중 하나라도 시뮬레이션이면(팔이 없거나 로봇이 Gazebo에 없으면)
다른 스텝과 똑같이 시간으로 진행한다 — 팔이 없다고 운영이 멈추지 않는다.

| 상황 | 처리 |
|---|---|
| 최초 진입 | `load` 지시 + 이력 기록. 스텝 진행 보류 |
| `loaded` 수신 | 스텝 즉시 완료 |
| `loadFailed` 수신 | `_failStep` — 태스크 재시도 대상 |
| 45초 무응답 | `abort` 보내고 **수동 적재로 전환**(자동 진행). 교착 방지 |

### 진행 정체 감시 (`_watchStall`)

관제는 통로 그래프만 알고 있어서, 현장에만 있는 장애물(팔 받침대·낙하물) 앞에
로봇이 갇히면 스스로 빠져나오지 못한다. **관제가 이동을 허용했는데도**
(`_speedOf > 0.05`) 로봇이 0.6 unit 이상 움직이지 못하면

| 경과 | 조치 |
|---|---|
| 25초 | 경로 재계획 + 경고 이력 |
| 55초 | 태스크 회수 → 대기열 반환(다른 로봇에 재할당) |

안전 정지·작업자 보호 필드로 서 있는 것은 정체로 세지 않는다.

### 도착 판정 반경

| 상수 | 값 | 용도 |
|---|---|---|
| `_linkReach` | 1.3 unit | 경유 웨이포인트. 로봇 값(1.2)보다 넉넉해야 관제가 영원히 기다리지 않는다 |
| `_linkGoalReach` | 5.0 unit | 종점. 로봇에 `goalTol`로 함께 전달 |

### 랙 정면 진입 (`_linkWaypoints`)

관제 경로의 종점은 랙 슬롯 좌표, 즉 **선반 중심선**이다. 통로 교차점에서 거기로
대각선으로 파고들면 실물 로봇은 선반 모서리에 막혀 슬롯 정면에 서지 못한다.

그래서 **로봇에 보내는 경로에만** 슬롯 바로 앞 통로 지점을 한 점 끼워 넣는다.
진입 통로는 직전 웨이포인트(또는 현재 위치)에 가까운 쪽을 고르므로 랙을
관통하지 않는다. 관제가 들고 있는 `Robot.path`는 그대로여서 시뮬레이션 로봇의
거동과 도착 판정은 영향을 받지 않는다.

```
관제 경로 :  … → (50, 6) → (54.3, 13)
로봇 경로 :  … → (50, 6) → (54.3, 6) → (54.3, 13)
                            ↑ 끼워 넣은 통로 진입점
```

### 배속 잠금

실장비가 하나라도 붙어 있으면 `effectiveSpeedMultiplier`가 1.0으로 고정된다.
현장 로봇은 실시간으로 움직이므로, 관제 시계만 4배로 흐르면 로봇이 유독 느려
보이고 처리량·배터리 지표가 왜곡된다. 상단 바 배속 선택기는 자물쇠 표시와 함께
비활성된다.

| 사이드바 하단 **현장 링크** | `게이트웨이 대기 :8788` / `실장비 n대 접속` / `게이트웨이 닫힘` |

## 11. 설계 판단 기록

통합 과정에서 실제로 부딪혀 고친 것들이다. 되돌리기 쉬운 형태로 기록해 둔다.

### 11.1 랙 도착 판정 — 왜 종점만 반경이 큰가

랙 깊이는 0.52 m이므로 중심선에서 표면까지 0.26 m다. 로봇이 선반 앞에 붙어도
중심은 중심선에서 약 0.41 m 떨어진다. 종점 반경이 경유점과 같은 1.2 unit(0.12 m)
이면 **어떤 로봇도 랙 슬롯에 도착할 수 없다.**

대안으로 랙을 얇게 만들 수도 있었지만, 그러면 창고가 창고처럼 보이지 않는다.
현장 로봇도 통로에 서서 슬롯에 접근하므로, Nav2의 `goal_tolerance`와 같은
개념으로 **종점만 0.5 m 반경**을 두는 쪽이 실제에 가깝다.

### 11.2 라이다 정지는 전진만 막는다

처음에는 전방 장애물이 감지되면 `cmd_vel`을 통째로 0으로 만들었다. 그 결과
슬롯 앞에 정지한 로봇이 **선반을 마주본 채 영영 돌아서지 못했다.** 다음 태스크가
와도 회전이 막혀 있어 경로를 시작할 수 없다.

지금은 추종기가 계산한 `(v, w)` 중 `v > 0`일 때만 `v`를 0으로 만든다. 회전은
항상 허용되므로 로봇은 선반에서 돌아서서 나갈 수 있다.

### 11.3 Gazebo GUI는 필수 프로세스가 아니다

`ros_gz_sim`의 `on_exit_shutdown`을 GUI 쪽에도 `true`로 두면 **GUI 창을 닫거나
렌더러가 죽을 때 물리 시뮬레이션과 관제 링크까지 함께 내려간다.** GUI에는
명시적으로 `false`를 주어, 창이 사라져도 시뮬레이션이 계속되고 `gz sim -g`로
다시 붙을 수 있게 했다. 전체 종료는 런치 터미널의 `Ctrl+C`다.

### 11.4 카메라 기본 비활성

`gz-sim-sensors-system`은 카메라·GPU 라이다마다 렌더 패스를 만든다. 통합 GPU
(Intel Iris Xe)에서 로봇 3대의 카메라를 켜면 GPU를 공유하는 다른 응용 —
**관제센터 창 포함** — 이 영향을 받는다. 관제 링크는 카메라를 쓰지 않으므로
기본을 끄고 `camera:=true`로 켜도록 했다.

### 11.5 메시 대신 기본 도형

## 13. 한계와 향후 과제

| 영역 | 내용 |
|---|---|
| **지역 경로 재계획** | 로봇은 관제의 통로 그래프 경로만 따른다. 통로 한복판의 예상 못 한 장애물 앞에서는 정지하고 이력에 사유를 올릴 뿐 스스로 우회하지 않는다. `pinky_agent`의 `cmd_vel` 출력을 Nav2 `navigate_to_pose` 액션 호출로 바꾸면 해결된다 |
| **프로토콜 표준화** | 자체 NDJSON 규약이다. 현장 배포 시 VDA 5050으로 정렬 필요 |
| **보안** | 인증·암호화가 없다. 루프백 또는 신뢰된 사설망 전제 |
| **측위** | odom 합성만 쓴다(드리프트 없음). 실기에서는 라이다 SLAM / AMCL 필요 |
| **동적 플릿 변경** | 관제 화면에서 링크 로봇을 등록 해제해도 Gazebo 쪽 로봇은 남는다. 재접속 시 다시 등록된다 |
| **작업자·환경** | 작업자 이동과 3온도 환경 변동은 여전히 관제센터 안의 시뮬레이션이다. 안전 필드는 그 값으로 계산되어 속도 상한에 반영된다. 물리 월드에는 작업자 모델이 없다 |
| **1대당 부하** | 로봇·팔마다 브리지 프로세스가 하나씩 붙는다. 대수가 늘면 브리지를 하나로 합치는 편이 낫다. 로봇 3대 + 팔 3대에서 gz CPU 97 % |
| **화물 파지** | 팔의 그리퍼 개폐와 궤적은 실제로 움직이지만 화물 객체가 손에 붙지는 않는다. 물리적 파지를 모사하려면 detachable joint나 흡착 플러그인이 필요하다 |
| **팔 배치** | 받침대 좌표가 `layout.dart` · `arms.yaml` · `generate_world.py` 세 곳에 중복되어 있다. 평면도를 바꾸면 세 곳을 함께 고쳐야 한다 |
| **적재 실패 복구** | 팔이 사거리 초과를 보고하면 스텝이 실패 처리되어 태스크가 재시도된다. 로봇을 더 가까이 재정차시키는 협상은 없다 |
